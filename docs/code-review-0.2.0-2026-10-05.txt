이번 검토는 기존 앱에 넣는 React SDK와 형식별 엔진을 중심으로 수행했다.
이전 리뷰의 네 문제에 대한 정식 회귀 검사는 통과했다. 기능 범위도 문단,
표, 그림, 검색·치환, 보고서 생성까지 확장됐다.
추가 시험에서는 SDK 구현의 새 문제 4건을 확인했다. P1 문제를 우선 수정해야 한다.
리뷰를 위해 제품 소스를 수정하지 않았으며, 별도 재현 호스트와 시험만 작성했다.

1. [P1] 잘못된 새 문서 입력 후 이전 편집본이 새 저장소에 전달됨

위치: D:\dev\document-studio\packages\react\src\document-editor.tsx:169-175

호스트가 열린 DocumentEditor에 다른 문서와 그 문서의 storage를 전달하는
조건에서, 새 문서 bytes가 ZIP 검증에 실패하면 오류만 표시하고 즉시 반환한다.
아래의 원본 교체 보호와 conflict 설정을 실행하지 않으므로 이전 문서의 session,
document, baseVersion이 살아 있는 상태에서 새 storage가 저장에 사용된다.

재현 호스트는 첫 파일을 편집한 다음, 손상된 두 번째 문서와 두 번째 파일의
저장소를 props로 전달했다. 검증 오류가 표시됐는데도 저장 버튼이 활성화돼
있었고, 저장을 실행하자 savedTarget='second-file', savedDocument='first-file'이 됐다.
DOCX·HWPX 모두 Chrome·Edge에서 재현했다.

이 결과는 모의 저장소로 확인한 SDK 호출 결과다. 실제 운영 파일을 덮어쓰는
시험은 하지 않았다. 새 대상에 이전 내용이 전달되는 조건 자체가 잘못된 파일
수정으로 이어질 수 있다.

수정 방향: 새 입력 검증 실패 시 저장을 차단하거나, 보존 중인 문서에 속한
저장소를 함께 유지한다. 문서 ID, 원본 버전, 저장 대상의 일치를 보장해야 한다.
단순히 오류 메시지만 닫아도 저장이 재개되는 구조는 피해야 한다.

2. [P2] 가로 DOCX 생성 시 너비와 높이가 뒤집힘

위치: D:\dev\document-studio\packages\engine-docx\src\templates.ts:101-104

createDocxDocument()의 page 설정에서 widthMm=297, heightMm=210,
orientation='landscape'를 전달하면 생성 결과가 약 210×297mm가 된다.
문서 XML도 w:w='11906', w:h='16838', w:orient='landscape'로 저장된다.

설치된 docx 라이브러리가 landscape일 때 width와 height를 자체 교환하는데,
SDK가 이미 가로 방향의 치수를 그대로 넘겨 다시 뒤집히는 것이 원인이다.
문서 생성 후 열어서 읽은 snapshot과 실제 XML을 함께 확인했다.
Chrome·Edge 모두 재현했다.

기존 문서에 pageSetup 명령으로 297×210mm를 적용하는 비교 시험은 통과했다.
따라서 이번 문제는 DOCX 문서 생성 factory의 치수 변환 경로에 해당한다.

수정 방향: DocumentTemplate의 공통 페이지 치수를 docx 라이브러리가 요구하는
입력 규약으로 변환한다. 생성과 기존 문서 수정의 치수 결과가 같아야 한다.

3. [P2] HWPX 문서 조회 API가 문장 안의 줄바꿈을 누락함

위치: D:\dev\document-studio\packages\engine-rhwp\src\index.tsx:489-501

에이전트 치환으로 '첫 문단\n둘째 문단'을 입력한 뒤 readDocument()를 호출하면
'첫 문단둘째 문단'으로 반환된다. 실제 저장 XML에는 다음 구조가 남아 있다.

<hp:t>첫 문단<hp:lineBreak/>둘째 문단</hp:t>

조회 코드가 hp:t의 textContent만 연결하므로, 빈 제어 요소인 hp:lineBreak를
줄바꿈으로 복원하지 않는 것이 원인이다. 파일의 줄바꿈은 보존되어 있으며,
이번에 확인한 문제 범위는 조회 API의 텍스트 표현이다.
Chrome·Edge 모두 재현했다. 같은 입력을 사용한 DOCX 조회 시험은 통과했다.

수정 방향: 텍스트와 hp:lineBreak 등의 제어 요소를 문서 순서대로 읽어
줄바꿈을 복원한다. 한 문단 안의 줄바꿈을 새 문단으로 강제할 필요는 없지만,
에이전트가 읽는 text에는 경계가 남아야 한다.

4. [P2] DOCX 강조색 상태가 잘못된 RGB 문자열로 반환됨

위치: D:\dev\document-studio\packages\engine-docx\src\docx-view.tsx:138-140

highlightColor 명령에 '#ffff00'을 전달해 노란 강조색을 적용한 뒤 getState()를
읽으면 highlightColor가 '#yellow'로 반환된다.

엔진이 Word 강조색 이름인 'yellow'를 반환하는데 SDK가 앞에 '#'만 붙인다.
공통 명령은 #RRGGBB를 요구하므로, 조회한 상태를 그대로 다시 적용하면
입력 검증에서 거절된다. Chrome·Edge 모두 재현했다.

수정 방향: Word 기본 강조색 이름을 공통 RGB 값으로 역변환한다. 혼합 상태와
강조색 없음은 별도로 처리하고, 적용값과 조회값의 왕복 시험을 추가한다.
