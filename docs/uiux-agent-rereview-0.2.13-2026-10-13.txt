1. 결론

0.2.12 재리뷰의 P2 1건과 P3 2건은 이번 직접 검증 범위에서 해결됐다.
같은 DOCX 재현 파일의 바깥 표는 1열로 반환됐고, 표시 이름 검색과 결과 없음
안내가 작동했다. 원본 옆에 구조 미리보기가 배치됐으며 접힌 평문 결과는
29px의 별도 영역으로 내려가 이전의 큰 빈 열이 사라졌다.

이번 검사에서 새 P1/P2 결함은 발견하지 못했다. 낮은 우선순위의 UI 안내
개선점 한 건은 남는다. 차트에는 현재 새 문서 생성이 연결되지 않았는데,
공통 설명은 새 문서 생성도 다음 행동으로 제안한다. 아래의 P3를 참고한다.

SDK의 보호와 기본 UI는 개선됐다. 이제 실제 General 에이전트가 이 SDK를
호출해 수정→저장→구조 확인→서버 재열기를 수행하는 업무를 완성해야 한다.
단위 테스트와 수동 SDK 호출 성공은 그 연결의 완료를 뜻하지 않는다.
인쇄용 명찰/명패와 채팅·문서 대조 UX도 이전에 명시한 후속 과제로 남아 있다.

2. 이전 지적의 수정 확인

P2 중첩 표 오보고 — 해결 확인.
0.2.12에서 사용한 자체 DOCX fixture를 그대로 사용했다. 바깥 1행×1열,
안쪽 2행×2열의 첫 행 병합 문서다. 실제 DOCX 엔진으로 열고 공개 agent.inspect와
같은 내보낸 XML의 직접 tblGrid/tcPr를 비교했다.
바깥 rows=1, columns=1, columnSpan=1.
안쪽 rows=2, columns=2, 첫 셀 columnSpan=2.
바깥 셀 text에는 바깥 시작/끝만 있고 안쪽 표 text가 중복되지 않았다.
수정된 직접 소유 속성 조회가 이 재현의 원인을 해결했다.

P3 표시 이름 검색 — 해결 확인.
실제 샌드박스에서 '내용 초안'은 명찰/회의명패 2개를 찾았다.
현재 선택은 '현재 선택 · 입력 유지' 정책으로 남고 검색 개수에는 포함되지 않았다.
없는 검색어에는 결과 없음과 선택/입력 유지의 이유가 표시됐다.
원래 금액 입력 12340은 검색 전후 그대로였다. 검색어는 비운 뒤 종료했다.

P3 접힌 평문 결과의 빈 열 — 해결 확인.
실제 화면에서 원본과 구조 미리보기가 좌우로 배치됐다. details는 입력 grid
밖에 있고 open=false일 때 높이가 29px이었다. 이전 355px 빈 결과 영역이
사라졌다. 실제 DOM 크기는 1920×945 CSS px, 원본/미리보기 각각 폭 381.5px였다.
원본 y=570.98, 미리보기 y=545.98로 같은 작업 영역에서 대조할 수 있었다.

이전 선택 오적용 P1 — 보호 유지 확인.
DOCX/HWPX에서 다른 문단으로 선택을 이동한 오래된 요청은 거절됐다.
선택을 유지한 정상 요청은 첫 문장만 수정하고 두 번째 문장을 보존했다.
이번에는 같은 문단의 모든 문자 범위·병합 셀·객체 선택을 새로 검사하지 않았다.

3. 이번 추가 검증

- SDK 단위 287/287과 yarn typecheck 통과.
- 프론트 설치 네 패키지가 모두 0.2.13이다.
- 설치 dist 95개 전체의 SHA-256이 SDK 빌드와 일치한다.
- SDK 소스·extension 49개를 시작/종료 해시로 비교해 변경 0개를 확인했다.
- 독립 실제 DOCX/HWPX 엔진에서 정상 에이전트 편집 후 commit의 digest가
  메모리 storage에 제출한 bytes의 SHA-256과 일치했고 dirty=false였다.
- HWPX 새 문서의 2×2 표는 셀 4개와 row/column/span/text가 올바르게 검사됐다.
- 계산 결과가 편집 가능한 상태로 유지됐고 직접 수정한 결과도 표시됐다.
- 차트 미리보기 img가 정상으로 나타났다.

독립 호스트의 storage는 메모리다. 실제 서버 쓰기나 서버 파일 재조회 검증으로
표시하지 않는다. 개발 세션의 프론트 610개/Chrome·Edge 614개/소비 앱 4개는
이번에 재실행한 숫자와 별개이며 합산하지 않는다.

4. P3: 차트의 다음 행동 안내가 지원 범위와 맞지 않는다

독립 HWPX 호스트에서 차트 미리보기를 만든 뒤 관찰했다.
- '그림을 선택 위치에 삽입'과 평문 삽입은 활성 상태다.
- '구조를 유지해 새 문서 만들기'는 비활성 상태다.
- 공통 설명에는 '새 문서는 원본 입력으로 만듭니다'와 '선택 위치에 넣거나
  새 문서로 만드세요'가 남는다.

관련 위치: packages/react/src/report-automation.tsx:786, 919.
차트는 graphic을 만들고 DocumentTemplate는 만들지 않으므로 새 문서 버튼이
비활성인 것은 현재 기능 범위와 맞는다. 설명도 그 범위를 따라야 한다.
'현재 문서에 그림으로 삽입할 수 있습니다'처럼 기능별 다음 행동을 안내하고,
생성이 지원되지 않는 버튼에는 이유를 보여주거나 불필요한 버튼을 숨기는 편이 좋다.
이번 변경에서 새로 발생한 회귀라고 판정하지 않고 현재 남은 작은 UI 안내 문제로 분류한다.

5. UI/UX와 최종 목적에 대한 다음 우선순위

1) 실제 General 연결과 업무 완료 확인.
SDK 브리지를 도구 transport에 연결하고 document/session/lease/선택 토큰을
검사한다. 요청 대상과 변경 항목, commit, inspect, 서버 재열기를 한 작업으로
완성한다. 실제 tool trace와 저장 버전/파일 해시를 함께 보관한다.

2) 사람과 에이전트의 대조 경험.
지금 원본/미리보기 배치는 좋아졌다. 다음은 채팅의 변경 항목과 문서 위치를
연결하고, 제어 주체·적용 대상·저장 확정을 보여주는 흐름이다. 문서 작업 모드와
좁은 화면에서도 채팅/문서/도구를 전환하며 맥락을 유지하는 경험이 필요하다.

3) 실제 업무 산출물.
명찰/회의명패는 내용 초안 범위를 유지한다. 실제 인쇄 업무를 제공할 때는
mm 치수/용지/한 쪽 개수/격자/재단선/접힘선을 계약으로 정하고 파일로 검증한다.

검토한 소비 프론트 production TS/TSX와 General Python에서 SDK 브리지
transport 등록은 여전히 확인되지 않았다. 기존 파일 에이전트의 능력을 부정하는
것이 아니라 열린 SDK를 실제로 호출한 증거가 없다는 판단이다.

6. 범위와 한계

실제 인증 샌드박스에서 기존 자체 검증 문서의 UI를 관찰했다. 문서 bytes나
채팅을 수정하지 않았고 실제 LLM 메시지/서버 저장/새 파일 업로드를 실행하지 않았다.
브라우저 입력 보관소에는 검증 작업의 기본 기능 선택이 반영될 수 있다.
최종 화면은 원래 금액 기능과 도구 닫기 상태로 복귀했다.

이번 실제 샌드박스 DOM은 1920×945였다. 1366/480px 전체 수용 시험은 개발
세션의 독립 호스트 결과이고 이번에 새로 재실행하지 않았다. 모바일 전체,
물리 IME/Word/한컴/프린터/운영 장애와 전체 접근성 준수는 검증하지 않았다.
새 P1/P2가 발견되지 않았다는 판정은 이 코드·문서·흐름의 검사 범위에 한정한다.

제품 소스 수정·커밋·푸시·공개는 하지 않았다. 리뷰 docs와 .build 검증 호스트/
증거만 작성했다. 임시 서버와 검증 탭은 종료했다.
