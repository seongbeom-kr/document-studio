판정과 변경
리뷰에서 이전 차트 안내 문제는 종료됐고 새 P1/P2는 없었다.
남은 P3는 작은 호스트에서 비율로 나눈 도구 본문이 42px까지 줄어드는 문제다.

SDK EditingTools가 업무 자동화 탭을 열 때 실제 폼 본문 높이를 측정한다.
본문이 360px 미만이면 기존 넓게 보기 상태로 전환한다. 호스트 영역의
크기 변경도 검사한다. 충분한 공간에서는 기존 문서/도구 배치를 유지한다.
사용자가 문서와 함께 보기로 돌아간 뒤 일반 재렌더링으로 다시 펼치지 않는다.
네이티브 편집기를 재마운트하지 않으며 문서 배율은 100%를 유지한다.

원본 입력 앞의 보관 상태·입력 길이·내려받기 항목은 원본 아래로 옮겼다.
결과가 없을 때 비활성 적용 버튼 영역을 sticky로 고정하지 않는다.
생성 미지원 호스트에는 새 문서 파일명과 저장 위치 입력을 숨긴다.
생성 지원을 켜면 원본을 유지한 채 파일명 입력과 생성 버튼을 사용할 수 있다.

초기 실패와 최종 실행을 구분한다.
첫 화면 검사에서는 작은 창의 입력 노출 부족과 테스트의 재열기 탭 가정을
발견했다. 입력 앞 항목/sticky 배치를 보완했고 재열기 후 자동화 탭을 다시
선택하도록 시험을 고쳤다. 보호 기능을 해제하거나 가용 높이 기준을 낮추지 않았다.
외부 소비 앱 첫 실행은 엔진 준비의 기본 expect 5초 조건에서 실패했다.
해당 준비 단계만 기존 page timeout과 같은 30초로 맞추고 실패 화면/로그와
준비 시간 기록을 추가했다. 재실행의 네 엔진 준비 시간은 885~2014ms였다.
프론트 첫 단위 실행은 종료코드 1과 596개만 기록했고 한 파일 14개가 빠졌다.
그 파일 단독 14개와 전체 610개를 다시 실행해 정상 종료를 확인했다.
프론트 버전 표시 파일의 CRLF lint 오류도 LF로 고친 뒤 lint가 통과했다.
각 초기 기록은 삭제하지 않고 별도 파일로 보관한다.

추가 확인: DOCX 서버 PDF 미리보기는 아직 실패한다
SDK native DOCX 편집은 정상으로 열렸지만 파일 미리보기로 돌아가면
files/preview?path=sdk-live-A.docx가 422를 반환한다. 재시도에서도 같았다.
이는 이번 자동화 탭 변경의 회귀로 확인한 결과가 아니다.
다운로드한 원본 SHA는 6703b076908563f61d3e34d53c18121e36b7b7579bfe8e80ffced0d624d1181b다.
ZIP CRC는 정상이며, 관측한 로컬 preview 이미지의 격리 컨테이너에서
LibreOffice 24.2.7.2로 같은 파일의 96,135-byte PDF 변환이 통과했다.
오래된 10월 8일 원본도 변환됐다. 따라서 파일 손상이나 암호화로 단정하지 않는다.
실제 요청을 처리한 worker와 실패 원인은 아직 특정하지 못했다.
운영 변환 경로를 수정하거나 오류를 숨기지 않았고 General/preview 서비스를
재시작하지 않았다. 이 서버 미리보기 경로를 정상 검증했다고 표시하지 않는다.
