1. 결론

0.2.11은 이전보다 사용하기 좋아졌다. 호스트 색상과 SDK의 연결, 표 구조
미리보기, 입력 보관 설명, 문서 저장과 자동화 입력 보관의 구분, 키보드 탭
이동과 도구 확대는 개선으로 인정한다. 실제 샌드박스도 이번에는 접속됐다.

그러나 사용자가 작업의 결과를 예측하는 경험과 에이전트가 작업을 확정하는
계약은 부족하다. 특히 에이전트의 서식·삽입 명령은 문서 identity와 revision을
검사해도 현재 선택 위치의 변경을 거절하지 않는다. DOCX/HWPX 실제 엔진
모두에서 첫 문장 요청이 두 번째 문장을 수정하고 applied:true를 반환했다.

UI에서는 표 미리보기와 같은 곳에 있는 '결과를 선택 위치에 삽입'이 실제
표가 아닌 텍스트를 삽입한다. 새 문서 생성은 표를 보존한다. 두 동작의 차이를
행동 직전에 설명해야 한다. 명찰은 카드 미리보기가 생겼지만 인쇄용 배치까지
완성된 기능은 아니다. 실제 DOCX 생성은 A4 일반 문단이었다.

판정: 기본 편집 SDK의 기능 검증과 사람이 신뢰하는 업무 도구의 완성도를
구분해야 한다. 현재 상태를 '에이전트가 SDK로 작업을 끝까지 잘 수행한다'고
평가할 근거는 부족하다. 최소 한 업무의 실제 도구 호출→수정→저장→재검증을
완성하고 그 작업을 사용자가 확인·복구할 수 있게 만드는 것이 다음 우선순위다.

3. 발견 사항과 우선순위

F1 [P1, 실제 엔진 재현] 에이전트 요청이 선택 위치 변경을 보호하지 못한다.
위치: packages/react/src/agent-bridge.ts:17, 31, 147-151
첫 문장을 select 후 documentId/sessionId/version/revision을 보관한다.
두 번째 문장으로 select만 이동하면 내용 revision은 여전히 0이다.
보관한 요청의 insertText를 실행하면 두 번째 문장이 [[AGENT-INSERT]]로
바뀌고 성공을 반환한다. 첫 문장은 그대로다. DOCX revision은 1,
HWPX revision은 2로 바뀌었다. 두 엔진의 selectionKey는 실행 전 달랐다.
이 검사는 사용자 입력을 직접 합성한 경합이 아니라 공개 select로 사용자
선택 이동과 같은 상태를 만든 재현이다. 실제 LLM/네트워크 경합은 미실행이다.
expectedRevision은 본문 수정 방어로는 작동했다. 선택에 의존하는 execute와
applyPreset의 대상 보장은 별도다. match/range에 묶인 원자적 명령이나
전체 선택 범위의 확인 토큰이 필요하다. 에이전트 상세 문서의 대안을 참고한다.

F2 [P2, UX 의미 불일치 재현] 표 미리보기의 '삽입'은 텍스트다.
위치: packages/react/src/report-automation.tsx:728-738
한 표가 있는 Markdown 결과를 미리보기하고 기존 문서에 삽입했다.
실제 DOCX/HWPX XML의 표는 0개였다. 내용은 탭/줄바꿈 텍스트로 들어갔다.
같은 원본으로 새 문서를 만들면 두 형식 모두 실제 표가 1개였다.
엔진이 표를 잃어버린 현상은 아니다. 현재 삽입 경로가 insertText이기 때문이다.
구조 미리보기는 생성 내용이라고 안내하지만 삽입 버튼의 형식 차이는 명시하지
않는다. '텍스트로 삽입 · 표/서식 제외'와 '구조를 유지해 새 문서 만들기'로
즉시 구분하고, 구조 삽입을 지원할 때 별도 명령과 검증을 제공해야 한다.

F3 [P2, 업무 완료 범위 부족] 명찰 카드 미리보기와 인쇄 산출물이 다르다.
위치: packages/core/src/templates.ts:84-117
세 참석자로 명찰을 만들면 미리보기는 카드 3개다. 생성된 DOCX는 A4
210.01×297.00mm, 여백 25.4mm, 표 0개, 이름/소속 6문단, 1쪽이었다.
카드의 물리 크기·격자·재단선·배치가 생성 계약에 없다. 카드 미리보기와
'명찰'이라는 기능 이름만으로 인쇄 가능한 명찰 완성이라고 판단하면 안 된다.
내용 초안이라고 범위를 명시하거나, 크기/용지/개수/배치가 있는 인쇄 템플릿을
제공하고 실제 생성 파일의 mm 치수를 검사해야 한다. HWPX 인쇄 결과는 이번
별도로 생성하지 않았으며 공통 template의 제한만 코드로 확인했다.

F4 [P2, 사용성 설계] 좁은 화면에서 문서·채팅·도구를 대조하기 어렵다.
1366×768에서 문서와 함께 보기의 HWPX iframe은 약 1024.6×258.7 CSS px였다.
도구 입력은 스크롤 아래에 있었고 확대하면 본문은 숨겨진다. DOCX 파일을
목록에서 다시 열었을 때 오른쪽 모달은 배경 채팅을 가렸다. 확대 도구 자체는
동작하지만 사용자와 에이전트가 같은 문서를 보면서 검토하는 작업에 불리하다.
화면/SDK/호스트를 합친 문제이므로 특정 CSS 한 줄의 오류로 단정하지 않는다.
작업별 편집 모드, 독립적으로 조절되는 도구 영역, 문서로 돌아갈 위치 보존,
선택 내용/적용 대상 표시와 채팅 결과의 변경 링크가 필요하다.

F5 [목적 달성의 선행 과제, 현재 라이브러리 계약의 오류 아님]
검토한 소비 프론트에는 createAgentBridge의 등록/명령 transport가 없었다.
브리지 메서드는 getState, listAutomationForms, listCommands, readDocument,
search, select, replace, applyPreset, execute의 9개다. save/commit,
새 문서 생성, 결과물 재검증은 노출하지 않는다. README도 transport를 호스트
책임이라고 명시한다. 기존 백엔드 파일 도구나 lease 보호가 SDK 연결의 증거는
아니다. SDK 연결과 에이전트 작업 완료를 별도 구현·수용 검사해야 한다.

F6 [목적 달성의 기능 격차] readDocument로 표 구조를 검증할 수 없다.
현재 공개 읽기는 paragraph id/text, 전체 text, revision, truncated, scope다.
실제 생성 XML의 표 1개는 읽기 결과에서는 셀 텍스트 문단으로만 드러났다.
행/열·셀 주소·병합·서식·그림 정보가 없으므로 '2×2 표를 만들었다'는 작업을
agent.readDocument만으로 확정할 수 없다. 명시된 API 범위와 일치하므로
허위 반환 버그로 분류하지 않는다. 구조 조회 또는 작업별 inspect가 필요하다.

4. UI/UX의 다음 개선 순서

즉시: 삽입 결과 형식을 명시하고, 적용 대상 선택 내용을 실행 버튼 옆에 표시한다.
생성 작업: 입력→구조 확인→이름/형식/목적 확인→생성→결과 문서로 이어지는
하나의 흐름을 만든다. structured 결과에서는 읽기 전용 평문 textarea를
기본 화면에서 줄이고 표/카드 미리보기를 주 결과로 보여준다.
도구 탐색: 20개 기능을 계산/표 정리/문서 작성/행사 자료 등 작업 목적별로
묶고 검색·최근 사용·예시 입력을 제공한다. 이름과 툴바만 추가하는 방식은
처음 사용자에게 어떤 기능을 선택해야 하는지 설명하지 못한다.
산출물: 제목 기반 파일명 제안과 저장 위치를 생성 전에 확인한다. 현재
보고서-무작위8자리 이름은 안전한 충돌 회피이나 문서 구분에는 도움이 적다.
가독성: 실제 자동화 textarea는 12px, 도움말은 11px이다. 입력과 상태 정보의
주요 글자 크기를 늘리고 약한 회색 안내의 역할을 정리한다. 대비 기준의
수치 측정 없이 WCAG 위반으로 단정하지는 않는다.

5. 에이전트가 실제로 SDK를 쓰기 위한 최소 범위

먼저 하나의 실제 업무를 고른다. 예: 문서의 특정 문구를 찾고 치환한 뒤
2×2 표를 넣고 저장하여 다시 읽는다. '아무 서식이나 설정할 수 있다'보다
이 과정을 두 형식에서 확실하게 수행하는 것이 목표에 가까워진다.

필수 계약은 대상 문서/세션/저장 버전 확인, 선택과 무관한 대상 지정,
지원 기능 조회, 구조 읽기, 고정된 대상 수정, 저장 확정, 저장 결과 검증이다.
사람에게는 변경 전후와 대상 표시, 에이전트 제어 상태, 저장 확정 상태,
실패한 단계와 재시도 방법, 되돌리기를 제공한다.

프론트 SDK가 브라우저에서 실행되는지, 백엔드가 별도 문서 실행기를 소유하는지
결정해야 한다. React/DOM/iframe 어댑터를 Python 서버가 바로 import할 수
있다고 가정하면 안 된다. 브라우저 실행이면 열린 편집기 및 연결 종료 정책,
기존 인증 BFF, lease 이양과 명령 응답 통로가 필요하다. 서버 실행이면 공통
core와 작업 계약을 재사용하되 별도 엔진 수명·저장·검증 경계를 마련한다.

처음 수용 검사에서는 실제 General 에이전트의 도구 trace, 수정 전후 문서,
서버 version과 파일 digest, 재열기 결과를 한 작업 단위로 보관해야 한다.
UI 버튼 성공이나 mock receipt만으로 실제 에이전트 사용 완료라고 판정하지 않는다.
