1. SDK에 대한 판정

이전 중첩 DOCX 표의 구조 오보고 P2는 같은 재현 파일로 해결을 확인했다.
DOCX와 HWPX에서 다른 문단으로 이동한 오래된 선택 요청이 거절되고,
정상 선택 요청은 해당 문장만 수정했다. 수정 후 commit의 digest와
메모리 storage에 제출된 실제 bytes의 SHA-256도 일치했다.
이번 코드/엔진 검사에서 새 P1/P2 결함은 발견하지 못했다.

이 결과는 SDK API와 실제 엔진의 제한된 흐름에 대한 판정이다.
최종 목적은 General 에이전트가 SDK를 도구로 호출해 문서 업무를 완료하는
것이다. 소비 프론트/General에서 그 transport 연결은 아직 확인되지 않았다.
수동으로 공개 API를 호출한 성공을 실제 LLM 에이전트 성공으로 표시하지 않는다.

2. 코드 변경과 설치 버전 확인

0.2.12 이후 변경은 중첩 표 속성의 직접 소유 범위 조회, 자동화 기능의
검색과 결과 표시, 관련 CSS/테스트였다. core inspect의 조회가 자손 표의
tblGrid와 tcPr까지 바깥 표 속성으로 읽지 않도록 바뀐 점을 중점 검토했다.
실제 엔진 재현으로 반환 구조가 원본 XML과 맞는지 확인했다.

소비 프론트 폴더 이름에는 0.2.11이 남아 있으나 설치된 SDK는 모두 0.2.13이다.
core 19개, react 22개, engine-docx 22개, engine-rhwp 32개 dist 파일을
SDK 빌드와 SHA-256 비교했다. 총 95개 중 불일치는 0개였다.
단지 package.json 버전 문자열만 일치하는 것으로 판단하지 않았다.

SDK 소스/extension manifest 49개는 검사 시작과 종료의 해시가 일치했다.
제품 소스는 이번 리뷰에서 수정하지 않았다. 최종 Git 상태도 확인했다.

3. P2 중첩 표 재현의 수정 검증

fixture: 이전 0.2.12 리뷰의 자체 nested.docx를 그대로 복사해 사용했다.
바깥 표 1행×1열의 셀에 안쪽 2행×2열 표가 있고 안쪽 첫 행은 병합돼 있다.
실제 DOCX 엔진으로 파일을 열고 공개 agent.inspect를 호출했다.
독립 비교 기준은 같은 문서에서 내보낸 XML의 직접 tblGrid/tcPr였다.

반환값: 바깥 rows=1, columns=1, columnSpan=1.
안쪽 rows=2, columns=2, 첫 셀 columnSpan=2.
바깥 셀 텍스트는 '외부 셀 시작외부 셀 끝'이며 안쪽 셀 텍스트가 중복되지 않았다.
따라서 에이전트가 이 문서의 바깥 표를 2열로 오해하던 재현은 해결됐다.

관련 소스: packages/core/src/inspect.ts.
inspect의 셀 텍스트는 text run을 이어 붙이는 정책이다. 문단 줄바꿈이
없는 것을 이번에 새로운 구조 손실 결함으로 분류하지 않았다.
모든 비정형/손상 OOXML, 복잡한 병합, 여러 단계 중첩의 포괄 검증은 아니다.

4. 선택 충돌과 정상 수정

실제 DOCX/HWPX 엔진에 두 문단을 가진 자체 문서를 열었다.
첫 문단: '첫 번째 대상 문장입니다.'
두 번째 문단: '두 번째 대상 문장입니다.'

충돌 재현: 첫 문단의 선택 키를 캡처한 뒤 두 번째 문단으로 이동하고
오래된 expectedSelectionKey로 guarded execute를 요청했다.
두 형식 모두 SelectionConflict 오류로 거절됐다.

정상 재현: 첫 문단을 다시 선택하고 새 키로 실행했다.
첫 문장만 '[[AGENT-INSERT]]'로 수정됐고 두 번째 문장은 보존됐다.
선택 이동과 문서 수정 사이에서 대상이 바뀌는 기존 P1에 대한 보호가 유지됐다.

이번 추가 검사 범위는 다른 문단으로 이동하는 경우다. 같은 문단 내의
모든 문자 범위, 이미지/표 객체 선택, 복수 사용자 동시 편집, iframe 교체,
모든 lease 경쟁 조건을 이번에 새로 검사한 것으로 해석하지 않는다.

5. commit과 생성 문서 검사

정상 편집 후 각 엔진의 공개 commit을 실행했다.
DOCX/HWPX 모두 receipt.digest가 메모리 storage에 제출한 bytes의
SHA-256과 일치했고 dirty=false였다. DOCX의 저장 호출은 1회,
HWPX 종료 시 두 엔진 합산 저장 호출은 2회였다.

이는 메모리 저장 검증이다. 실제 서버 API의 수락, 파일 버전 충돌,
다운로드/재열기까지 검사한 결과와 구분한다.

추가로 자체 Markdown의 2×2 표를 HWPX 새 문서로 만들었다.
이름은 '0.2.13 구조 확인.hwpx'였고 공개 inspect가 4개의 셀과 올바른
row/column/span/text를 반환했다. truncated=false였다.
실제 General 채팅이나 개발 샌드박스 서버의 파일을 새로 만들지 않았다.

6. 실제 에이전트 사용을 위한 다음 완료 기준

검토한 소비 프론트 production TS/TSX와 General Python에서
createAgentBridge / expectedSelectionKey / document_studio / document-studio
관련 transport 등록은 확인되지 않았다. 기존 파일 에이전트가 다른 방식으로
문서를 처리할 수 있는지와 별개로, 열린 SDK를 호출한 증거가 아직 없다.

첫째, document/session/lease/선택 토큰을 포함하는 실제 도구 호출을 연결한다.
에이전트가 inspect로 대상을 찾고 변경 계약을 만들며 execute/commit 결과를
구조화된 도구 결과로 받아야 한다. 브라우저의 전역 객체를 발견하는 것만으로
도구 등록이 완료된 것으로 간주하지 않는다.

둘째, '첫 문단만 변경하고 다른 문단은 유지', '표 한 셀만 변경', '2×2 표
생성' 같은 작은 업무를 실제 LLM으로 수행한다. 어떤 파일/세션에 적용했는지,
선택이 바뀌었을 때 재확인하는지, 실패를 성공으로 보고하지 않는지 확인한다.

셋째, execute 후 commit, inspect, 서버 재열기를 연결한다.
서버에 보관된 버전과 파일 해시를 기록하고 재열린 문서에서 변경 결과를
검사한다. timeout, 저장 충돌, stale selection은 오류 종류별로 드러내며
실패 시 중복 적용을 피하는 흐름도 실제 transport를 통해 검증한다.

넷째, 채팅에 저장된 파일과 완료 상태를 연결한다.
사람이 변경 위치와 결과를 확인하고 업무 완료를 판단할 수 있어야 한다.
SDK 오류 문자열을 그대로 사용자 안내로 노출하기보다 다음 행동을 제공한다.
위 내용은 통합 완료 기준이며 이번에 입증한 새로운 코드 결함 목록은 아니다.
