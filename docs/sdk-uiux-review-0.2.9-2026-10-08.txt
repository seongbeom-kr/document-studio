Document Studio SDK 0.2.9 UI UX 재검토
검토일: 2026-10-08 KST
대상: D:\dev\document-studio
동등한 비중의 코드 리뷰: sdk-adversarial-review-0.2.9-2026-10-08.txt

판정

이전보다 사용 흐름이 분명해졌다. 결과 미리보기의 수정 규칙, 원본 입력으로 돌아가기,
자동화 입력 복구, 키보드 도구 탐색, 긴 입력의 작업 공간이 개선됐다.
단순히 버튼이 추가된 것을 확인하는 데서 그치지 않고 실제 Chrome UI로 동작을 대조했다.

이번 UX 검증은 독립 SDK host에서 수행했다.
실제 샌드박스 앱은 백엔드 연결 장애와 서버 중단으로 검증하지 못했다.
따라서 현재 호스트 브랜드/배치, 실제 파일 목록 전환, 서버 오류에서의 복구 UX까지
완료됐다고 평가하지 않는다.

1. 결과 미리보기와 원본 수정: 해결 확인

참석자 명단에 검증용 두 사람을 입력하고 미리보기를 실행했다.
결과 textarea의 readOnly=true를 실제 DOM에서 확인했다.
'새 문서는 원본 입력으로 만듭니다. 결과 미리보기는 읽기 전용입니다.' 안내가 나타났다.
'원본 입력 수정'을 누르면 참석자 정보 입력란으로 실제 포커스가 이동했다.

이전처럼 사용자가 결과를 고치자 생성 버튼이 갑자기 꺼지는 혼란은 줄어든다.
수정 위치를 원본 입력으로 통일하고 오래된 template로 문서를 생성하지 않는 방향은 타당하다.
일반 평문 계산 결과의 직접 편집과 문서형 결과의 읽기 전용 규칙도 코드에서 구분된다.

남는 개선
명단 결과는 여전히 평문/탭 구분 텍스트다.
표, 명찰, 명패처럼 시각 배치가 중요한 기능은 다음 단계에서 실제 표/카드 미리보기가 있으면 좋다.
읽기 전용이 됐다는 사실을 시각적 문서 미리보기가 완성됐다는 의미로 해석하지 않는다.
이는 이번에 새로 찾은 실행 실패가 아니라 남는 제품 개선 제안이다.

2. 닫기와 재열기 후 자동화 원본 입력: 일반 크기에서 해결 확인

독립 host에서 browserAutomationDraftStore를 opt-in하고 전용 합성 사용자 namespace를 사용했다.
참석자 명단에 아래 입력을 넣었다.
검증전용A,문서팀,검토자
검증전용B,개발팀,담당자

저장으로 보관 완료를 기다린 뒤 SDK 편집기를 닫고 같은 문서를 다시 열었다.
업무 자동화는 참석자 명단으로 복원됐고 두 줄의 원본 입력도 동일했다.
이 경로의 자동화 자료는 Map 대역이 아니라 실제 Chrome IndexedDB에 보관됐다.
같은 편집 세션 안의 메모리 유지보다 한 단계 넓은 복구를 직접 확인했다.

안내
'자동화 입력은 이 브라우저에 별도로 보관됩니다. 닫고 다시 열어도 복구할 수 있습니다.'가 표시된다.
보관 대상과 문서 저장이 다르다는 점을 설명하는 방향도 이전보다 낫다.
이것은 다른 브라우저/기기와 동기화되는 서버 저장 기능은 아니다.

새로 남은 문제
코드 리뷰에서 1,000,001자를 보관 성공으로 처리한 뒤 다음 열기에서 거절하는 경계를 재현했다.
원본 textarea에는 최대 길이 제한이 없었다(maxLength=-1).
사용자에게는 보관 완료 안내를 신뢰한 뒤 복구가 막히는 경험이 될 수 있다.
큰 입력의 한도, 오류 위치, 수정/다운로드 및 정상 초안 보존 경로가 필요하다.
같은 근본 문제를 코드/UX 두 건으로 중복 집계하지 않는다.

검증 범위
일반 크기의 실제 IndexedDB 복구는 브라우저에서 수행했다.
100만 자 경계는 AutomationSession과 store 대역을 사용한 클래스 시험이다.
실제 Chrome에 대용량 초안을 기록해 복구하는 시험을 수행했다는 뜻은 아니다.

3. 키보드 탭 탐색과 패널 관계: 해결 확인

'표' 탭에 포커스를 두고 ArrowRight를 눌렀다.
선택과 포커스가 '그림'으로 이동했다.
선택한 탭만 tabindex=0이고 나머지 7개는 -1이었다.
각 tab의 aria-controls와 대응 tabpanel/aria-labelledby가 연결된 것을 확인했다.
Home/End 및 순환 이동 처리도 코드에 추가됐다.

Escape 복귀도 검증했다.
확대된 도구에서 Escape를 누르면 문서와 함께 보기로 돌아오고,
다시 Escape로 도구를 닫으면 문단·표·그림 열기 버튼에 포커스가 돌아왔다.
키보드 사용자가 도구를 닫은 뒤 다음 위치를 잃는 문제가 줄어든다.

이 결과는 키보드/DOM 검증이다. 스크린 리더 제품별 수용 시험이나 전체 접근성 인증은 아니다.

4. 도구 크게 보기: 해결 확인

일반 화면과 1366x768 viewport에서 '도구 크게 보기'를 사용했다.
긴 입력과 결과를 편집 작업 영역 전체에서 살펴볼 수 있었다.
노트북 크기에서 관찰한 확대 도구 영역은 약 1227x468 CSS px였다.
이 수치는 독립 standalone host의 값이며 이전 실제 샌드박스 모달 치수와 일대일 비교하지 않는다.

확대 중에도 원래 native Document content DOM은 1개 유지됐고 본문은 inert 상태였다.
도구 확대 때문에 문서 엔진을 제거하거나 새로 여는 방식은 아니었다.
참석자 원본 입력은 확대와 Escape 복귀 후에도 그대로 남았다.

이전의 좁은 도구 패널에 긴 원고를 억지로 넣는 불편을 완화하는 유효한 개선이다.
실제 샌드박스의 모달/크게 보기 전환과 함께 쓰는 모습은 서버 복구 후 추가 확인해야 한다.

5. 문서 생성 결과의 구조: 독립 엔진에서 정상 확인

DOCX
마크다운으로 제목, 한글 본문, 2열 표를 만들었다.
실제 DOCX 엔진이 생성 자료를 열었고 public readDocument에서 제목·본문·표 셀 텍스트를 확인했다.

HWPX
마크다운으로 제목, 별도 본문, 표, 표 뒤 문단을 만들었다.
실제 RHWP/WASM 엔진이 자료를 열었고 public readDocument에서 다음을 확인했다.
- 첫 문단: SDK 0.2.9 문단 검증
- 두 번째 문단: 제목과 분리된 본문입니다.
- 표 셀: 항목/결과/생성/확인
- 후속 문단: 표 뒤의 마지막 문단입니다.

제목과 본문이 합쳐지거나 맨 앞에 빈 문단이 생기는 기존 생성기 문제는 이 자료에서 보이지 않았다.
표를 담기 위한 빈 anchor 문단까지 오류로 집계하지 않았다.

중요한 구분
이 host의 생성 결과 보관/열기는 메모리 구현이다.
실제 샌드박스 서버의 신규 업로드, lease release, 파일 목록 갱신과 재열기 성공을 뜻하지 않는다.
한컴/Word 프로그램으로 같은 자료를 여는 호환성 검사를 새로 수행한 것도 아니다.

6. 여전히 확인해야 할 실제 사용자 작업

백엔드가 복구되면 다음 흐름을 우선 검증해야 한다.

첫째, 실제 DOCX/HWPX 편집 중 사용자 데이터로 새 문서를 만든다.
원문서 마지막 입력이 저장되고 새 파일이 한 번만 생성돼야 한다.

둘째, 업로드/반영/새 문서 열기 중 실패하게 하고 다시 시도한다.
기존 편집권 재확보 전에는 입력을 허용하지 않아야 한다.
실패 후 원래 문서와 자동화 원본 입력이 유지되고 사용자가 상태를 이해할 수 있어야 한다.

셋째, 응답이 늦거나 유실된 뒤 재시도한다.
이미 저장된 산출물을 중복 생성하지 않고 확인/열기로 이어져야 한다.

넷째, 실제 좁은 파일 패널과 문서 크게 보기 사이를 오간다.
현재 선택, 문서 내용, 자동화 입력, 키보드 포커스를 잃지 않아야 한다.

다섯째, 서버 저장 상태와 브라우저 입력 보관 상태가 다른 경우를 표시한다.
보관 실패 안내가 가려진 채 버튼이 아무 반응이 없는 것처럼 보이지 않아야 한다.

7. 추가 개선 제안

자동화 입력의 길이/복구 안내
글자 수 제한은 보관 실패 후가 아니라 입력 시점에 알아볼 수 있어야 한다.
보관할 수 없는 큰 입력을 조용히 잘라내지 말고 수정하거나 내려받을 수 있게 한다.

미리보기의 구조
문서형 기능은 최종 문서의 표·카드·쪽 나눔을 판단할 수 있게 발전시키는 것이 좋다.
현재의 원본 수정/읽기 전용 규칙은 유지할 수 있다.

저장 상태 문구
standalone 헤더의 '모든 변경사항 저장됨'은 문서와 자동화 입력을 함께 떠올리게 할 수 있다.
문서 저장 상태와 입력의 로컬 보관/메모리 상태를 가까운 위치에서 명확히 구분하면 더 좋다.
별도 보관 안내가 추가됐으므로 이것을 또 하나의 새 코드 결함으로 집계하지 않았다.

샌드박스 디자인의 최종 평가
독립 SDK host는 standalone 기본 테마를 사용한다.
이를 샌드박스의 실제 색상, 레이아웃, 오류 처리 모습으로 오해하면 안 된다.
실제 서비스 화면이 연결되면 그 화면에서 전체 UX를 다시 평가해야 한다.
