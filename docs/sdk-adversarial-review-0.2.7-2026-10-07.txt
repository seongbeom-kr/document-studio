1. [P1] 새 문서 전환의 마지막 저장 뒤에도 입력할 수 있어 최근 변경이 빠진 채 전환된다

수정 위치: 프론트
apps/sandbox-agent/app/_components/workspace/document-edit-session.tsx:148-169
apps/sandbox-agent/app/_components/workspace/document-edit-session.tsx:508-521
apps/sandbox-agent/app/_components/workspace/file-preview-panel.tsx:463-474

handoff는 saveRef.current()가 끝난 뒤 suspended.current=true로 polling을 중지하고
편집 lease release 응답을 기다린다. 그러나 suspended는 EditingContext.blocked나
content의 inert에 반영되지 않는다. SDK save가 끝나면 편집기 자체의 busy/inert도 해제된다.

release 응답을 지연시키자 그 사이 실제 SDK가 새 편집 명령을 받아 dirty=true가 됐다.
그 상태에서 release를 완료하면 마지막 변경을 다시 저장하거나 revision을 검사하지 않고,
FilePreviewPanel이 dirty를 false로 바꾸고 생성 파일 열기를 호출했다.

DOCX/HWPX 문서 경로 모두에서 다음 상태를 관찰했다.
- release 대기 시작: SDK busy=false, readOnly=false, 편집 본문 inert=false.
- 대기 중 새 편집: SDK dirty=true, 현재 export bytes=[2].
- 보관된 마지막 저장본 bytes=[1]. 원문서 업로드는 추가되지 않았다.
- 새 파일 열기 호출 발생. SDK는 여전히 dirty=true인데 부모 dirty는 false.

실제 부모는 생성 파일을 previewFile에 설정해 기존 편집기를 unmount한다.
3초 자동 초안 저장 전에 전환되면 이 구간의 입력을 잃을 수 있다.
단순히 업로드 중 입력을 저장하는 문제와 구분되는, 마지막 저장과 잠금 해제 사이의 틈이다.

재현 방식
실제 FilePreviewPanel, DocumentEditSession, DocumentStudioPanel, 설치된 SDK를 함께 사용했다.
문서 엔진과 API/초안 저장소는 통제 가능한 시험 대역이다. 유효한 생성 결과를 받은 뒤의
public onCreateDocument 경로를 호출하고 release 응답을 지연시켰다.
이 시험은 DOCX/HWPX native codec이나 실제 인증 서버에서 수행한 시험이 아니다.

수정 방향
마지막 저장부터 release 완료·문서 전환까지 사용자 입력과 SDK 쓰기를 계속 잠근다.
lease를 해제하기 직전에 문서/세션/권한/revision과 미저장 상태를 다시 확인한다.
늦은 변경이 있으면 저장을 반복하거나 전환을 취소한다. native HWPX 입력 차단도 2번과 함께 고쳐야 한다.

증거: .build/sdk-review-0.2.7/handoff-docx.json, handoff-hwpx.json

2. [P1] HWPX의 포커스된 내부 입력창은 readOnly=true 이후에도 본문을 바꾼다

수정 위치: SDK와 RHWP 엔진 연결
packages/react/src/document-editor.tsx:348-350
packages/react/src/types.ts:8-15
packages/engine-rhwp/src/index.tsx:344

공통 SDK는 readOnly일 때 명령을 거절하고 부모 .ds-editor-body에 inert를 설정한다.
하지만 EngineViewProps에는 readOnly 전달 계약이 없고, RHWP 내부 입력창의 편집 상태는 바뀌지 않는다.
HWPX iframe 안의 '문서 편집 입력'에 이미 포커스가 있으면 부모 inert만으로 입력을 막지 못한다.

직접 브라우저 재현
1. 자체 fixture HWPX를 실제 RHWP 엔진으로 연다.
2. iframe 내부 입력창에 포커스를 둔다.
3. DocumentEditor의 readOnly=true를 반영한다. 굵게 버튼 비활성화와 부모 inert=true를 확인한다.
4. Playwright keyboard.type("READONLY7")로 일반 키 이벤트를 보낸다.
5. export한 Contents/section0.xml의 본문에 READONLY7이 추가되고 SDK dirty=true가 된다.
6. 별도의 keyboard.insertText 한글 입력도 문서에 추가된다.

Chrome과 Edge 모두 재현했다. 같은 DOCX 시험은 두 브라우저 모두 본문 변경 없이 통과했다.
afterPhysicalKeys라는 관찰 필드명은 Playwright의 키 이벤트 주입 단계를 가리킨다.
실제 물리 Windows 키보드/IME 시험을 수행했다는 뜻이 아니다.

서버 파일 저장이나 서버 ACL 우회까지 확인한 결과는 아니다.
그러나 SDK 읽기 전용 계약이 깨지며, 프론트가 편집권을 잃었을 때도 로컬 본문이 바뀔 수 있다.
저장·전환 중 입력 동결 역시 같은 부모 inert를 사용하므로 이 방식만 믿을 수 없다.

수정 방향
유효한 편집 가능 상태를 EngineViewProps/EditorSession과 iframe bridge에 전달하고,
RHWP native 입력/편집 계층에서 쓰기를 거절한다. 기존 포커스와 진행 중 조합 입력도 처리한다.
읽기 전용, 저장 중, 편집권 상실 각각에서 내부 포커스를 유지한 채 키 입력·붙여넣기·조합을 검사한다.

3. [P2] 늦은 저장 알림이 바뀐 문서 또는 새 편집기의 미저장 표시를 지운다

수정 위치: 프론트
apps/sandbox-agent/app/_components/workspace/document-studio-panel.tsx:206-220
apps/sandbox-agent/app/_components/workspace/file-preview-panel.tsx:285-290

saved(event)는 시작 시 문서 ID를 확인하지만 onRefresh()를 await한 뒤에는 다시 확인하지 않는다.
그 다음 latest.current.props.onSaved(false)를 호출하므로 A의 저장 완료가 B의 콜백을 부를 수 있다.
unmount 후에도 이어지는 콜백을 취소하지 않는다.

재현 1
A 저장 알림의 onRefresh를 지연 → Panel props를 B로 교체 → B를 dirty=true로 설정 →
A의 refresh 완료. B.onSaved(false)가 호출되고 B의 부모 dirty가 false가 됐다.

재현 2
A의 refresh 대기 중 Panel을 unmount → 새 B Panel을 mount하고 dirty=true로 설정 →
A의 refresh 완료. 이전 Panel의 onSaved(false)가 공유 부모 dirty를 false로 만들었다.
두 경우 모두 B의 SDK dirty=true 상태는 그대로였다.

실제 FilePreviewPanel.onEditorSaved는 상위 onEditingDirtyChange(false)를 호출하므로
부모의 파일 전환 보호와 현재 문서의 미저장 상태가 달라질 수 있다.
원래 정상 전환 경로에는 저장 대기 보호가 있지만, 외부 props 변경/unmount 이후의
늦은 callback 자체도 현재 문서에 영향을 주지 않아야 한다.

재현은 실제 Panel 소스 콜백과 통제한 SDK/API 경계로 수행했다.
인증된 UI에서 자동/외부 문서 전환 경로 전체를 수행한 결과로 확대해서 해석하지 않는다.

수정 방향
refresh 전후에 mount 상태, 사용자/세션/문서 generation을 확인한다.
시작 시 캡처한 문서의 저장 알림을 다른 문서의 최신 callback으로 보내지 않는다.
부모 dirty를 해제하기 전에 현재 SDK의 dirty/pendingCommands/저장 상태도 확인한다.

증거: .build/sdk-review-0.2.7/late-saved-replacement.json, late-saved-unmounted.json

앞선 정정 유지

0.2.6 리뷰에서 철회한 제목의 인라인 그림 사례를 새 결함으로 다시 집계하지 않았다.
표 셀의 별도 paint 보정과 재시도/입력 보존 수정은 소스 및 기존 기록에서 확인했다.
이번 새 결함은 해당 개선이 없다는 주장과 다르다.

검증 한계

- 인증된 https://sblim.dev.gridone.net/sandbox-agent에 대한 브라우저 접근 제한은 유지했다.
  인증 정보 주입·다른 주소를 통한 우회를 하지 않았다.
- 브라우저 검사는 자체 fixture와 별도의 localhost SDK 시험 서버를 사용했다.
  실제 인증 BFF/lease/운영 저장 계약은 이번에 시험하지 않았다.
- 호스트 race는 실제 SDK/프론트 코드에 통제한 엔진/API를 연결한 시험이다.
- 한컴 native 및 물리 Windows IME 시험은 미수행이다.
- 제품 코드, 작업 문서, 권한/배포 설정을 변경하지 않았다. 재기동이나 푸시도 하지 않았다.
