1. 판정

처음 자동화 입력을 찾고 작성하는 경험은 개선됐다. 공간이 부족하면
도구를 넓게 열고 입력 앞의 반복 정보를 아래로 옮겨, 이전의 42px 본문
문제를 독립 임베딩 호스트에서 해결했다. 넓게 보기를 명시적으로 해제한
사용자의 선택도 일반 재렌더링 후 유지됐다.

원본→미리보기→다시 원본 보정 단계에는 P3 한 건이 남는다. 낮은 창에서
결과를 만들면 하단 적용 영역이 원본을 덮어 다시 한두 줄만 보이게 된다.
입력 전의 가용 공간만 검사해서는 작업 흐름 전체의 사용성을 판단할 수 없다.

이번 실제 샌드박스 문서 화면은 General API 502로 열지 못했다.
아래 문서 UI 수치는 실제 DOCX/HWPX 엔진을 사용한 독립 SDK 호스트 결과다.
개발자가 전날 기록한 실제 샌드박스 화면 결과를 오늘 직접 검증한 것으로
표시하지 않는다. 실제 사용자 연구나 전체 업무 완료 시험도 아니다.

2. 이전 P3 해결 확인

조건: appearance=embedded, 호스트 1023×646, CSS 화면 1366×900,
기본 도구 크기 34. 이전 리뷰의 편집기 영역 크기를 동일하게 지정했다.
두 형식 모두 자동화 탭에서 확장되고 본문 높이는 약 434.6px였다.
원본 입력은 270px가 보였고, 기능 선택과 미리보기 버튼이 본문 안에 있었다.
scrollTop=0, 가로 넘침 없음, 원본의 +40px 좌표도 실제 textarea에 도달했다.
공개 상태의 문서 배율은 100%였고 선택한 문장도 유지됐다.

수동 복귀: 문서와 함께 보기를 누른 뒤 호스트의 생성 지원을 껐다 켰다.
두 형식 모두 data-expanded=false가 유지됐다. 단순 재렌더링이 사용자의
복귀 결정을 곧바로 뒤집지 않았다. 호스트 영역 자체를 줄이면 자동 확장되는
동작과 일반 재렌더링은 구분해 검사했다.

생성 지원 없음: 파일명 입력이 숨겨지고 생성 버튼은 비활성이다.
생성 지원 있음: 원본을 보존한 채 파일명 입력과 생성 버튼이 다시 제공됐다.
지원하지 않는 호스트에 불필요한 파일명 입력이 보이던 이전 개선 권고도 반영됐다.

3. P3: 결과가 생기면 고정 적용 영역이 원본을 덮는다

재현 순서
1) CSS 화면 1366×768, 호스트 1023×514에서 자동화 탭을 연다.
2) 마크다운 보고서에 제목과 2×2 표를 입력한다.
3) 결과 미리보기를 눌러 구조 미리보기가 완성될 때까지 기다린다.
4) 내부 스크롤을 움직이지 않은 상태에서 원본과 결과를 비교한다.

두 형식 모두 재현됐다. HWPX의 미리보기 전/후 본문 높이는 약 302.6px,
textarea와 본문의 교집합 높이는 약 140.3px다. 미리보기 전에는 원본 +40px가
textarea에 도달하지만 결과가 있으면 적용 영역에 도달한다.
원본 y=372.69, 적용 영역 y=411.87, 고정 영역 높이=101.14px였다.
원본에서 가리지 않고 남는 높이는 약 39.18px다.

모바일 HWPX: CSS 480×900, 호스트 456×700.
본문 383.28px, 기하학적 원본 노출 177.41px지만 고정 영역을 제외하면
약 55.48px만 남았다. 원본 +80px 지점은 textarea 대신 적용 버튼이었다.
원본 +40px 한 점의 검사만으로는 이 모바일 가림을 놓칠 수 있다.

영향: 결과를 보고 표 데이터/문단을 고치는 단계에서 원본을 다시 스크롤해야
한다. 구조 미리보기의 아래쪽 내용도 바로 대조하기 어렵다. 입력 자체가
삭제되거나 저장이 실패한 것은 아니며 스크롤로 접근할 수 있어 P3로 분류한다.
이번 버전에서 최초 생긴 회귀라고 단정하지 않는다.

4. 원인과 완료 기준

packages/react/src/styles.css:311–316이 결과가 있으면 적용 행 전체를
sticky bottom:0으로 고정한다. 버튼 두 개와 긴 공통 설명이 함께 고정돼
낮은 본문에서 실제 입력 공간을 소비한다.
packages/react/src/report-automation.tsx:933–935의 설명도 그 행 안에 있다.

긴 설명을 고정 영역 밖으로 옮기고 고정 영역을 짧은 버튼 행으로 줄이거나,
가용 본문 높이가 낮으면 sticky를 해제하는 방식을 권한다. 버튼을 계속
보이게 하는 이점과 원본을 보정하는 공간 사이의 우선순위를 조정해야 한다.

완료 기준: 미리보기 전뿐 아니라 생성 후에도 원본의 최소 80px가 실제로
가리지 않고 보이며, 그 범위의 클릭 좌표가 textarea에 도달한다.
기능 선택·미리보기·원본 보정·삽입/생성 행동을 한 흐름으로 확인한다.
두 형식, 낮은 노트북 창, 모바일 폭을 포함한다.

현재 새 E2E의 공간/가림 검사는 결과 생성 전에 실행된다.
tests/e2e/automation-workspace.spec.ts:100–107 이후 115–126에서는
결과 표시와 스크린샷만 검사한다. 같은 검사를 결과 생성 후에도 반복하고,
sticky 영역과의 겹침을 고려해야 한다. 스크린샷 저장만으로 합격시키지 않는다.

5. 실제 샌드박스에서 오늘 확인한 상태

첫 접속은 Gateway Timeout이었다. 개발 프론트를 sblim scope로 재실행한
뒤 페이지와 인증 UI는 열렸지만 작업 목록과 그룹 API가 502였다.
화면은 'General Agent에 연결할 수 없습니다.'를 표시했다.
따라서 오늘 기존 문서의 실제 drawer 배치나 미리보기·서버 저장은 재검증하지 못했다.
General 서비스나 설정을 변경해 실패를 우회하지 않았다.

전날 개발 기록의 DOCX PDF 미리보기 422도 오늘은 파일 접근 전에 막혀
재검증하지 못했다. 실패를 최신 수정의 회귀/파일 손상으로 단정하지 않는다.
연결을 회복한 뒤 DOCX 읽기 전용 미리보기→편집→다시 미리보기의 흐름을
확인해야 한다. 화면마다 서로 다른 성공 상태를 보여주면 사용자가 불안해진다.

6. 최종 목적에 대한 UI 우선순위

실제 General 연결을 회복한 뒤 에이전트의 변경 위치와 파일을 연결한다.
사용자가 어느 문단/셀을 바꾸는지, 무엇이 달라졌는지, 어떤 버전이 저장됐는지
채팅과 문서에서 대조할 수 있어야 한다. 이 전체 경험은 아직 확인되지 않았다.

명찰/회의명패는 내용 초안과 실제 출력물의 경계를 유지한다. 인쇄 업무로
확장할 때 mm 치수·용지·배치·재단/접힘선을 계약으로 검증한다.
실제 사용자 업무를 대표하는 '수정하고 저장본을 다시 열어 확인' 시나리오를
앞세워야 하며 도구 화면별 성공만으로 편집 업무가 완성됐다고 판단하지 않는다.

7. 범위와 종료 상태

독립 호스트의 화면은 CSS 크기로 확인했다. 기존 브라우저 배율을 변경하지
않고 viewport 요청 크기를 조정해 실제 innerWidth/innerHeight를 맞췄다.
문서 배율은 100%였다. 임시 viewport override를 해제하고 검증 탭/서버를 종료했다.
실제 파일·채팅은 변경하지 않았으며 합성 문서만 사용했다.
개발 프론트 두 앱은 재실행 상태로 유지했다. 제품 구현 소스를 직접 수정하지 않았다.
물리 IME·Word/한컴·인쇄·전체 접근성·모바일 전체 업무 완료는 미검증이다.
