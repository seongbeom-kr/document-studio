1. 사람이 쓰기 좋아졌는가

미리보기 뒤 원본을 고치는 흐름은 분명히 좋아졌다. 0.2.15에서는 낮은 창에서
적용 버튼이 입력칸을 덮었는데, 0.2.16에서는 같은 조건의 독립 DOCX/HWPX에서
이 문제가 재현되지 않았다. 원본을 키보드로 보정하고 결과 제목을 다시 만드는
일련의 동작까지 통과했다. 이번 수정 목적에는 합격이다.

다만 실제 HWPX가 준비 상태에서 장시간 멈추는 장면은 사용자가 즉시 체감할
문제다. 입력칸이 좋아져도 문서를 열지 못하고 기다리기만 하면 작업을 시작할 수
없다. 사용성의 다음 우선순위는 초기화 실패의 안내·재시도다.

2. 이전 P3 종료 근거

수정 코드:
D:\dev\document-studio\packages\react\src\styles.css
D:\dev\document-studio\packages\react\src\report-automation.tsx

결과가 있을 때 .ds-automation-actions를 sticky로 만드는 규칙이 삭제됐다.
긴 설명은 버튼 행 밖의 문단으로 이동했다. 결과 전후로 레이아웃이 다른
겹침 규칙을 갖지 않게 됐고, 실제 적중 검사도 이를 뒷받침한다.

두 형식, appearance=embedded, 업무 자동화 자동 확장, 마크다운 제목+표를 사용했다.
- CSS 1366×768 / 호스트 1023×514: 결과 생성 후 입력 노출 약 140.3px.
- CSS 1366×900 / 호스트 1023×646: 약 270.0px.
- CSS 480×900 / 호스트 456×700: 약 177.4px.
각 화면에서 원본 안쪽 +4/+40/+79px 모두 textarea에 적중했다.
적용 영역은 static이며 검사한 도구 영역의 가로 넘침은 없었다.

낮은 창에서는 원본 상단으로 이동해 키보드로 글자를 바꾸고 미리보기를 다시
생성했다. DOCX '수정 DOCX 검증', HWPX '수증 보고서' 제목 갱신을 확인했다.
후자는 키보드 시험에서 한 글자만 치환한 합성 문구이며 실제 사용자 내용이 아니다.
변경한 것은 자동화의 원본 입력이며 현재 문서 본문은 그 시점에 바뀌지 않았다.

실제 DOCX에서도 기존 76자 입력을 바꾸지 않고 결과 미리보기를 생성했다.
CSS 1366×768, 편집기 약 1024×537.3에서 원본은 약 172.6px 노출됐고
세 적중 지점이 모두 textarea였다. 기존 제목의 0.2.11은 파일 내용이다.
설치 버전은 별도로 dist 해시와 패키지 0.2.16을 확인했다.

3. P2 — 준비 대기에서 빠져나오는 길이 없다

실제 sdk-live-B.hwpx는 서버에서 파일을 받아도 빈 편집 영역과 준비 중 상태가
94.6초 이상 이어졌다. 오류·재시도 안내는 없었다. 대기를 계속할지, 원본에
문제가 있는지, 다시 열어야 하는지 사용자가 판단하기 어렵다.

독립 정상 HWPX는 열렸지만, iframe HTML 응답만 지연시키면 70.9초 이상 같은
무한 준비 상태가 나타났다. SDK의 초기 iframe load에 전체 제한 시간이 없다는
코드 근거와 일치한다. 실제 샌드박스에서 iframe이 멈춘 근본 원인은 미확정이다.
이 문제를 새 CSS 변경의 회귀나 문서 훼손으로 표현하지 않는다.

권장 사용자 흐름:
- 파일 받기 → 편집기 연결 → 문서 열기처럼 진행 단계를 간단히 표시한다.
- 설정된 제한 시간을 넘으면 준비 중 대신 '편집기를 연결하지 못했습니다'와
  다시 시도/파일 목록으로 돌아가기 같은 실제 가능한 선택지를 보여 준다.
- 실패 중인 문서를 닫거나 전환할 때 원본에 편집이 있었는지 명확히 구분한다.
- 재시도는 이전 iframe/비동기 작업이 남지 않도록 SDK 취소 처리와 함께 구현한다.
구체적 원인을 모르는 상태에서 사용자의 네트워크나 파일 탓으로 안내하지 않는다.

4. 이후에 더 좋아질 수 있는 점 — 확정 결함과 구분한 제안

A. 낮은 창에서 원본과 결과의 읽기 공간을 선택할 수 있게 한다.
140px 정도면 간단한 수정은 가능하지만 여러 문단·큰 표를 대조하기에는 짧다.
현재의 원본/미리보기 병렬 배치를 유지하면서 '원본 크게', '결과 크게' 전환을
제공하면 사용자가 창 크기와 작업 목적에 맞게 읽을 수 있다. 위치를 계속 찾도록
만드는 고정 하단 버튼을 다시 도입하는 방식은 이번 해결을 되돌릴 위험이 있다.

B. 기능 목록보다 작업 목적을 찾기 쉽게 한다.
실제 화면은 '기능 찾기' 입력과 긴 '자동화 기능' 선택 목록을 제공한다.
초기 진입에서 어떤 말을 검색할지 알 수 있도록 '표 정리', '금액을 한글로',
'마크다운으로 보고서 만들기' 같은 예시나 최근 기능을 제시할 수 있다.
고급 기능을 제거하라는 제안이 아니라 첫 선택의 부담을 낮추자는 제안이다.

C. 세 가지 저장 상태를 가까운 곳에서 구분한다.
자동화 원본의 브라우저 보관, 현재 문서의 수정 여부, 서버 작업 공간 저장은
서로 다르다. 화면에는 관련 안내가 있지만 사용자는 미리보기 후 저장이 끝났다고
이해할 수 있다. 원본/결과 옆에 '브라우저 보관됨', 적용 뒤 문서 상태에
'문서에 반영됨·서버 저장 필요', 저장 성공 뒤 '작업 공간 저장됨'을 간결하게
연결하면 작업을 마쳤는지 판단하기 쉽다. 이번 시험에서 상태 오표시 결함을
재현한 것은 아니므로 개선 과제로 분류한다.

D. 에이전트와 사람의 적용 대상을 함께 보여 준다.
선택 내용·대상 문단 안내는 이미 도움이 된다. 에이전트가 실제로 수정할 때도
어느 문서의 어느 범위를 바꿨고 저장까지 끝났는지 결과를 사용자 언어로 보여
주면 좋다. 내부 sessionId/revision/hash를 일반 사용자 화면에 나열할 필요는 없다.
개발자 도구에는 해당 근거를 제공해 오작동을 추적할 수 있게 한다.

5. 실제 서비스 관찰의 변화

이 URL은 sblim 개발 샌드박스이며 공개 운영 서비스라고 판정하지 않았다.
sessions/session-groups는 이번에 200, DOCX PDF preview도 200 및 화면 표시가
확인됐다. 이전 502/422를 현재 장애로 반복 기재하지 않는다.
HWPX 서버 preview 요청 자체는 200이었으나 native 편집 초기화는 완료되지 않았다.

원본 다섯 파일 목록을 전후 확인했고 sdk-live-A.docx r5와 sdk-live-B.hwpx r7의
해시·리비전은 유지됐다. 실제 자동화 입력 76자도 유지했다. 사용자 파일 저장이나
업로드, 채팅 전송은 하지 않았다. 편집 권한 획득/해제와 미리보기 열기만 수행했다.

6. 범위와 판단

Chrome의 실제 샌드박스 DOCX 및 독립 DOCX/HWPX 반응형 흐름을 직접 검사했다.
모바일 수치는 좁은 CSS viewport에서의 입력 가림 검사다. 휴대폰 터치 키보드와
전체 업무 완료를 검증한 것은 아니다. 전체 접근성·스크린리더·물리 IME·인쇄도
보증하지 않는다. 확인한 개선을 인정하되 제품 전체 UX 완성 판정으로 확대하지 않는다.
