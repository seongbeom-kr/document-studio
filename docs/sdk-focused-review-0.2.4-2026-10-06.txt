1. [P2] 검색 조건과 선택한 치환 대상이 연결되지 않는다

코드 위치, 13:50의 0.2.4 소스 기준
- packages/react/src/editing-tools.tsx:173-180: 비동기 검색 결과 반영
- packages/react/src/editing-tools.tsx:759, 780, 789: 검색 조건 변경
- packages/react/src/editing-tools.tsx:801-812: 선택 결과 치환
- packages/react/src/editing-tools.tsx:849-853: 비동기 결과 선택 완료

실제 DOCX 화면 재현
1) 독립 SDK의 DOCX 예제를 연다.
2) 검증을 검색하고 공개 편집 검증 문서 결과를 선택한다.
3) 찾을 내용을 한국어로 바꾼다. 새 검색은 아직 실행하지 않는다.
4) 바꿀 내용에 SDK검색시험을 넣는다.
5) 선택 결과 바꾸기가 계속 활성화되어 있어 누른다.

결과
화면의 찾을 내용은 한국어지만 제목은 공개 편집 SDK검색시험 문서로 바뀌었다.
본문의 한국어 문장은 그대로였다. 현재 조건 대신 이전 조건의 선택 대상이 치환됐다.
이 DOCX 변경은 Undo로 복구했다.

HWPX 비교
HWPX에서도 검증 결과 선택을 완료한 뒤 찾을 내용을 한국어로 바꾸면 이전 선택 치환 버튼이 활성화됐다.
버튼 실행 후 1개 바꿈 결과를 확인했다.
HWPX 선택 명령은 비동기이므로 완료 직전의 일시적인 비활성 상태와 완료 후 활성 상태를 구분해 관찰했다.
후속 원문 스크린샷과 Undo 확인은 브라우저 도구 연결 지연으로 완료하지 못했으므로 DOCX와 같은 수준의 최종 원문 대조라고 주장하지 않는다.
조작한 것은 로컬 합성 예제이며 서버의 사용자 문서를 변경한 것은 아니다.

추가 실패 주입 재현
같은 revision에서 예전 검색 응답을 지연시키고 새로운 검색 결과를 먼저 완료했다.
화면의 입력은 새로운인데, 나중에 도착한 예전 응답이 결과 목록을 예전으로 덮었다.
목록 버튼도 활성 상태라 선택과 치환으로 이어질 수 있다.
최신 0.2.4의 React 컴포넌트에서도 동일 시험이 실패했다.

원인
- query/matchCase/wholeWord 변경은 results와 selected를 무효화하지 않는다.
- 선택 치환 활성 조건은 selected와 문서 revision만 확인한다.
- search 함수는 요청 세대나 검색 조건을 확인하지 않고 await 이후 setResults를 수행한다.
- 문서 revision이 같아도 검색 조건은 서로 다를 수 있다.

권고
검색 조건의 식별값과 요청 세대를 함께 관리한다.
조건 변경 시 기존 결과·선택을 즉시 해제하고, 늦게 도착한 검색/선택 응답은 버린다.
치환 버튼은 현재 조건과 결과가 일치하고 현재 결과 안에 선택 대상이 있을 때만 활성화한다.
새 검색 중 상태도 표시한다.

2. [P2] 서식 preset 실행 중 readOnly로 바뀌어도 후속 쓰기를 계속한다

코드 위치
- packages/react/src/document-editor.tsx:595의 시작 시 readOnly 검사
- packages/react/src/document-editor.tsx:645-652의 순차 실행 루프

재현
실제 SDK DocumentEditor에 제어 가능한 가짜 엔진을 연결했다.
1) fontSize → alignCenter → paragraphFormat으로 구성된 제목 서식 preset을 시작한다.
2) 첫 fontSize 명령 응답을 지연시킨다.
3) 호스트가 DocumentEditor의 readOnly prop을 true로 바꾼다.
4) 첫 명령을 완료한다.

결과
readOnly=true가 된 뒤에도 alignCenter와 paragraphFormat이 새로 호출됐다.
preset Promise는 실패하지 않고 성공으로 완료됐다.
첫 번째 이미 전달된 명령의 취소 가능 여부와 별개로, 아직 전달하지 않은 명령까지 실행하는 문제다.
최신 0.2.4 소스에서도 재현했다.

원인
입구에서만 readOnly와 지원 여부를 검사하고, await 이후 반복되는 session.execute 사이에는 다시 검사하지 않는다.
같은 SDK의 save/export에는 추가된 세션·상태 보호가 preset 루프에는 없다.

영향과 범위
호스트가 문서를 읽기 전용으로 전환한 이후에도 메모리의 문서 서식이 바뀔 수 있다.
서버 lease나 인증을 우회해 저장한다는 뜻은 아니다. 그 부분은 호스트/서버의 별도 검사 대상이다.

권고
각 후속 명령 전 현재 document/session과 readOnly·취소 상태를 검사한다.
중단했을 때 전체 롤백 또는 어느 단계까지 적용됐는지 명확한 결과를 반환한다.
이미 전달된 첫 명령과 아직 전달하지 않은 후속 명령을 구분해 회귀 시험을 유지한다.

증거
- sdk-state-current.test.tsx
- 실제 호출: fontSize, alignCenter, paragraphFormat / rejected=false
- 기대: fontSize만 전달, 이후 거절

3. [P2] DOCX 강조색 선택 UI가 엔진이 거절하는 입력을 그대로 제공한다

코드 위치
- packages/react/src/editing-tools.tsx:263-272의 자유 RGB 색상 입력
- packages/react/src/editing-tools.tsx:283-294의 강조색 적용
- packages/engine-docx/src/commands.ts:62-72의 Word 기본 16색 검사

재현
실제 EditingTools의 색상 입력을 사용자 change 이벤트로 #245f56으로 바꾸고 강조색 적용을 눌렀다.
execute를 실제 DOCX nativeCommand 어댑터에 연결했다.
버튼은 활성화되지만 다음 실행 오류가 발생했다.
DOCX 강조색은 Word의 기본 16색만 지원합니다. 예: #ffff00(노랑).

대조
같은 UI/어댑터에서 #ffff00은 정상 동작했다.
즉 지원하지 않는 arbitrary RGB를 안전하게 거절하는 어댑터 자체는 맞다.
사용자가 실행 전에 지원되는 선택을 할 수 있게 만들지 못한 UI 계약이 문제다.

확인 범위
이 색상 실패는 컴포넌트 입력 이벤트와 실제 어댑터로 확인했다.
브라우저 자동화의 native color input fill은 React 상태에 제대로 전달되지 않아 실제 선택값이 검정으로 적용됐다.
이 도구상의 제약을 DOCX 색상 버그 재현으로 세지 않았다.
00-color-input-automation-limitation.png도 색상 오류의 증거로 사용하지 않는다.

권고
DOCX 강조색은 지원되는 16색 팔레트를 제공한다. 글자색과 강조색 선택기를 구분한다.
HWPX의 자유 RGB와 DOCX의 제한 팔레트를 엔진 capability/constraints로 UI에 전달한다.
버튼의 supported/enabled만으로 유효한 파라미터까지 보장하지 않는다.
숫자 범위, 적용 범위, 셀 선택 필요 여부 등도 같은 방식으로 실행 전 안내해야 한다.

증거

- current-results.json

4. 사용성이 낮게 느껴지는 구체적인 이유

우선순위 높음: 보고서 서식 한 번 적용과 Undo 한 번이 대응하지 않는다
본문의 한국어를 선택했을 때 원래는 10pt·왼쪽 정렬이었다.
보고서 제목 버튼 한 번으로 16pt·가운데·문단 뒤 12pt를 적용했다.
Undo 한 번 뒤에도 16pt와 가운데 정렬은 남았다. 총 3번 Undo해야 10pt·왼쪽으로 복구됐다.
현재 문서에도 순차 Undo 제한을 명시해 두었으므로 새 회귀라고 분류하지 않는다.
그러나 사용자에게는 한 번의 서식 적용이므로 문서화만으로 좋은 사용성을 만들지는 못한다.
명령 묶음의 원자적 적용·Undo를 제공하고, 중간 실패도 전체 복구할 수 있게 하는 것이 좋다.
증거: 04-preset-partial-undo.png, packages/core/src/presets.ts, applyPreset 루프.

우선순위 중간: 문단·페이지의 사용자 수치와 엔진 내부 정밀도를 분리한다
DOCX 예제의 페이지 UI에서 A4 너비가 210.0086111111111mm,
높이가 297.00361111111107mm로 표시됐다.
단위 변환의 내부 정밀도를 잘못된 문서라고 판단하지는 않는다.
표시는 사용자에게 필요한 소수 1~2자리로 정리하고 내부 원본 값은 유지한다.
빈 값도 미확인과 혼합을 구분해 보여주면 사용자가 현재 상태를 더 신뢰할 수 있다.
페이지/문단에서 변경한 항목이 무엇인지 표시하고, 변경이 없으면 적용 버튼을 비활성화하는 편이 좋다.
증거: 05-page-values-raw-precision.png.

우선순위 중간: 업무 자동화 입력을 기능별로 설계한다
금액, 만 나이, 기간, 추첨, 조직도 등이 같은 입력과 추가 인수 필드를 공유한다.
추가 인수는 어떤 기능에서는 기준일, 어떤 기능에서는 인원수나 구분 조건이다.
기능 이름을 선택했을 때 그에 맞는 필드 이름, 예시, 기본값, 오류 안내를 제공한다.
기능을 바꿀 때 이전 기능의 날짜/텍스트가 그대로 남아 사용자가 형식을 추측하게 만들지 않는다.
이 항목은 소스/UI 구조 검토에 따른 개선안이며 20개 자동화의 실제 브라우저 합격 판정은 아니다.

우선순위 중간: 그림 삽입의 기본값과 문서 맥락
공통 그림 도구는 너비 40mm·높이 30mm를 독립 입력한다.
원본 비율 유지, 문서 폭 안에 맞춤, 삽입 위치 안내를 제공하면 시행착오가 줄어든다.
표 편집도 현재 셀·선택 범위와 작업 영향을 설명해야 한다.
특히 DOCX의 비활성 셀 병합/분할은 형식별 지원 차이라는 점을 쉽게 확인할 수 있어야 한다.
그림 변형이나 모든 병합 표의 원본 보존을 이번에 실제 문서로 보증한 것은 아니다.

긍정적으로 바뀐 점
- 문단·표·그림과 삽입·쪽 메뉴로 진입점 이름을 구체화했다.
- 페이지 너비에 맞춤 기능과 작은 컨테이너의 별도 배치가 추가됐다.
- 직전 작업이라는 결과 표시로 작업 이력과 현재 상태를 구분하려는 수정이 들어갔다.
- 진행 중 명령이 busy/pendingCommands에 나타나고 저장 직전 명령 완료를 기다린다.
- 같은 version의 자기 저장도 승인된 bytes로 비교한다.
위 UI 새 기능 전체를 좁은 화면과 두 엔진에서 합격 검증한 것은 아니므로 구현 확인과 검증 통과를 구분한다.

실제 브라우저 확인
- 독립 SDK DOCX/HWPX 합성 예제를 열었다.
- DOCX 검색 선택 후 검색 조건 변경 및 이전 대상 치환을 재현하고 Undo로 복구했다.
- HWPX에서도 이전 검색 대상 유지와 1개 치환 결과를 확인했다.
- DOCX 보고서 제목 서식 적용과 3단계 Undo를 확인했다.
- DOCX 표 2행×2열에서 행 삽입 후 3행×2열, Undo 후 2행×2열을 확인했다.
- DOCX 페이지 가로 방향 적용 후 세로 방향으로 Undo한 값을 확인했다.
- 브라우저 도구 연결/명령 전달 지연이 여러 차례 발생했다.
  이를 SDK 자체의 렌더링 성능이나 문서 처리 지연 수치로 해석하지 않았다.

미검증 범위
- 이번에는 서버 저장·lease·인증·에이전트 handoff를 재검증하지 않았다.
- 전체 Chrome/Edge E2E, 실제 Windows 한글 IME, 한컴/Word native 앱 대조를 다시 수행하지 않았다.
- 대용량 실무 문서, 복잡한 구역/머리말/각주/추적 변경, 깊은 병합·중첩 표의 전수 호환성은 보장하지 않는다.
- HWPX 후속 Undo와 종료 확인 일부는 브라우저 도구 지연으로 완료하지 못했다.
  외부 작업 공간 파일은 수정하지 않았고 검토용 로컬 예제만 사용했다.
- 코드에 수정안을 적용하거나 공개 배포하지 않고, 리뷰와 격리된 시험만 추가했다.
