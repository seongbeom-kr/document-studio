Document Studio 0.2.19 — 소비 앱의 UI 구성 API
2026-10-15 / Asia/Seoul

범위
0.2.18의 범용 DOM 연결·HWPX 입력 보존을 검증하고 커밋한 뒤 진행했다.
이번 버전은 소비 앱이 툴바·상태 표시·편집/자동화 패널의 위치와 모양을 소유하도록
하는 UI 단계다. 실제 General transport와 편의작업 통합 dispatcher는 추가하지 않았다.

SDK 계약
- ui.containers.toolbar/statusBar/tools에 호스트의 HTML 요소를 전달한다.
  React와 DOM API가 같은 옵션을 사용한다. 미지정 영역은 기본 위치에 표시한다.
- 툴바·상태·편집 도구는 안정된 portal 대상으로 렌더링한다. 목적지를 바꿔도
  엔진·도구 폼을 재마운트하지 않으며 입력·선택·포커스를 유지한다.
- 대상의 기존 자식은 보존하고 SDK 소유 요소만 추가·이동·제거한다.
  분리된 DOM, 다른 document, SDK 내부 요소는 대상으로 받지 않는다.
- ui.theme의 색·글꼴·모서리 토큰을 편집기와 외부 영역에 같이 적용한다.
  문서 내용의 글꼴이나 용지 확대는 바꾸지 않는다.
- React slots.toolbar/statusBar는 기본 UI, 상태, guarded execute, 도구 탭 열기,
  native 메뉴와 확대 제어 함수를 받는다. DOM API는 React render 슬롯을 받지 않는다.
- 커스텀 슬롯 렌더링 실패는 해당 영역의 기본 UI로 복구하고 오류를 표시한다.
  저장 경고·초안 복구·확인창·오류 안내는 교체 가능한 슬롯에 넣지 않는다.
- DOM 전환·종료 동안 외부 도구도 inert 처리한다. 초안 보관 실패 시 편집기와
  도구를 유지하며 재시도할 수 있다. 메모리 자동화 입력의 폐기 보호도 유지한다.
- 외부 tools의 크기는 호스트가 정한다. 내부 도킹 크기·자동 전체 확장을 강제하지
  않는다. 예제는 모바일에서 문서 아래에 충분한 높이의 도구 영역을 배치한다.

프론트 로컬 적용
DocumentStudioToolbar와 DocumentStudioStatus가 플랫폼 Button/디자인 토큰을 사용한다.
기본 서식·찾기·업무 자동화·native 메뉴·페이지 수·확대를 host-owned 영역에 연결했다.
기존 저장·다운로드·편집권/lease·동기화 재시도 흐름은 유지했다.
프론트의 기준 커밋·브랜치를 추가 갱신하지 않았으며 커밋·푸시하지 않는다.

검증 중 보완
첫 신규 UI Chrome 시험은 12개 중 10 통과/2 실패였다. DOM update의 입력 잠금이
패널 이동 때 포커스를 해제해 입력 값은 유지되지만 커서가 사라졌다. 잠금 해제 후
기존 SDK 영역의 연결된 요소에 포커스를 복원하고 해당 두 형식을 재검증했다.
이후 좁은 화면에서 툴바의 flex 최소 폭으로 가로 넘침이 발생했다. 최소/최대 폭을
설정하고 외부 자동화 원본 입력의 높이를 보완했다. 예제의 모바일 패널 높이도
조정하고 실제 보이는 입력 높이를 측정하는 검사를 추가했다.

전체 회귀에서는 일부 이전 HWPX 키보드 시험이 selectAll 호출만으로 native 입력창에
포커스가 생긴다고 가정한 것을 확인했다. 0.2.18의 React 소스를 분리한 비교 호스트와
같은 엔진에서도 selectAll 뒤 body가 활성 상태였고, 명시적으로 입력창에 포커스를
주면 정상 입력됐다. 4개 파일의 키보드 시험에 실제 입력창 포커스를 추가했다.
XML 내용·미저장 상태·초안 복구·형식·서버 저장에 대한 검증 조건은 그대로 유지했다.
전체 실행 중인 원본 시험은 수정하지 않고 별도 복사본으로 먼저 재검증했다.
복사본의 Chrome/Edge × DOCX/HWPX 관련 250/250이 통과했으며, 전체 실행 완료 후
검증한 파일과 같은 바이트를 원본 시험에 적용했다. 제품 런타임은 이 시험 보완으로 바뀌지 않는다.

전체 732개 실행은 689 통과/43 실패였다. 42개는 위 포커스 준비 문제였다.
나머지 1개는 HWPX 저장 직후 다시 열 때 불필요한 초안 복구창이 생긴 경우였다.
해당 파일 재실행은 42/42 통과했지만 반복 12회에서는 3회 실패해 실제 경합으로
분류했다. native 이벤트 호출 스택에서 flushDeferredPaginationIfNeeded가 저장된
revision 5 이후 revision 6을 만들고 dirty=true로 바꾸는 것을 확인했다.

원인은 RHWP의 지연 페이지 계산 알림을 SDK가 새 편집으로 센 것이다. 고정 엔진의
deferred-pagination-flush:* / deferred-pagination-complete 및
input-handler-resumable-pagination 알림만 revision에서 제외했다. 실제 입력과
cell-overflow 편집, 알려지지 않은 변경 이유는 계속 추적한다. 초안을 강제로 삭제하거나
미저장 보호를 우회하지 않는다.

실제 native event bus에 관찰된 지연 계산 알림을 저장 이후 주입하는 회귀 시험을
추가했다. 이전 handler는 저장 revision 5가 7로 바뀌어 실패했고, 수정 후 두 브라우저가
통과했다. 이어서 실제 새 입력은 dirty=true가 되고 저장·종료·재열기에도 남는지 확인한다.
이 시험의 이벤트 순서 주입과 실제 타이머를 사용하는 반복 시험을 구분한다.

한계
실제 인증된 샌드박스 사이트는 브라우저 도구의 저장된 권한 정책에 의해 접근이
차단된 상태여서 우회하지 않았다. 실제 General LLM→열린 SDK→서버 저장 성공을
검증했다고 표시하지 않는다. 자동 테스트는 로컬 합성 문서와 격리된 호스트를 쓴다.
HWPX 첫 연결 지연 원인, Word/한컴 전체 호환성, 물리 IME, 인쇄·전체 접근성,
범정부 오피스 전체 기능 일치는 별도 후속 범위다.
