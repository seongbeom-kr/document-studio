1. 전체 평가

이전 버전의 산만한 도구 집합에서 공통 편집기 모양으로 정리된 것은 개선이다.
호스트의 보라색 버튼/탭과 상속 글꼴을 사용하고, SDK의 제목·저장 헤더를
embedded 모드에서 생략한다. 사용자는 호스트의 파일 헤더와 저장 버튼을 쓴다.
기능이 실제로 열리고 미리보기와 생성이 동작한다는 점도 확인했다.

다만 사용성의 핵심은 버튼 수와 도구 수가 아니다. 사용자가 다음 행동을
고르고, 바뀌는 대상과 결과를 예상하고, 생성 문서가 자신의 업무 목적을
충족했는지 확인할 수 있어야 한다. 현재는 원본 입력·평문 결과·구조 미리보기,
선택 위치 삽입·새 문서 생성의 관계를 사용자가 직접 이해해야 한다.

특히 에이전트와 사람이 함께 쓰는 제품이라면 채팅의 요청, 문서의 변경,
저장 확정이 이어져야 한다. 지금 '에이전트 대기 중' 문구와 '이 파일로 질문'
버튼은 보이지만 에이전트의 변경 제안/대상/적용/완료를 보여주는 경험은
검토한 편집 화면에서 확인하지 못했다. 실제 agent run은 이번 실행하지 않았다.

2. 이번에 확인한 개선

- 실제 자동화 원본 92자가 HWPX를 닫아 파일 목록으로 돌아갔다가 재진입한 뒤
  그대로 복원됐다. 미리보기 결과는 다시 계산해야 했다. 결과가 문서 bytes와
  별도로 보관되는 것처럼 오해시키는 영구 결과 복원 주장은 하지 않는다.
- 마크다운의 제목·본문·표·표 뒤 문단을 구조 미리보기로 구분할 수 있다.
- 결과 textarea는 구조 생성 기능에서 읽기 전용이고 '원본 입력 수정'을 제공한다.
- 문서 저장과 브라우저 입력 보관을 다른 상태로 안내하는 source가 반영됐다.
  실제 저장 장애를 주입한 검증은 개발 세션 결과이며 이번에 새로 실행하지 않았다.
- 실제 HWPX 재진입에서 배율 100%를 확인했다. 맞춤/100%의 선택 UI가 있다.
- Tab 목록에서 표→ArrowRight는 그림을 선택하고 포커스를 이동했다.
  선택 탭만 tabindex=0, 나머지는 -1이었다. 확대 도구에서 Escape는 함께 보기로,
  다음 Escape는 도구 닫기로 이어지고 문단·표·그림 버튼으로 포커스가 돌아왔다.
- DOCX/HWPX 새 문서 생성의 실제 XML에는 미리보기의 표가 1개 들어갔다.

3. P2: 표를 보고 삽입했는데 텍스트만 들어가는 경험

재현 원본:
# 표 삽입 검증
본문입니다.

| 항목 | 결과 |
|---|---|
| SDK | 확인 |

독립 호스트의 실제 DOCX/HWPX를 열고 업무 자동화→마크다운 보고서→결과
미리보기를 실행했다. 두 행/두 열의 표가 화면에 나타났다. '결과를 선택 위치에
삽입'을 실행하고 공개 exportDocument로 얻은 XML을 검사했다. 표는 0개이고
'항목\t결과', 'SDK\t확인'이 평문으로 삽입됐다. 동일 원본의 '새 문서로 만들기'는
실제 표 1개를 만들었다.

현재 구현은 report-automation.tsx:734의 insertText 경로다. 표 생성 실패나
파일 손상이라고 보고하는 것은 부정확하다. 사용자에게 전달하는 행동의 의미가
명확하지 않은 것이 문제다. 새 문서가 원본으로 만들어진다는 설명은 있지만
기존 문서 삽입이 표/서식을 제외한다는 설명은 버튼 가까이에 없다.

개선:
1) 당장 버튼을 '텍스트로 삽입'으로 변경하고 '표·글자 서식 제외'를 붙인다.
2) 새 문서 버튼은 '구조를 유지해 새 문서 만들기'로 역할을 구분한다.
3) 이후 구조 삽입을 제공할 때 일반 텍스트와 표/블록 삽입을 별도 선택으로
   제공하고 현재 선택을 덮어쓰는지, 앞/뒤에 추가하는지 확인하게 한다.
4) 성공 상태는 '텍스트 4줄 삽입' 또는 '표 2행×2열 생성'처럼 실제 결과를 말한다.

수용 기준: 미리보기와 다른 결과를 내는 행동에는 실행 전 명시적인 범위 안내가
있고, 생성/삽입 후 실제 XML과 UI 성공 문구가 일치한다.

4. P2: 명찰 기능은 인쇄 가능한 명찰까지 완료되지 않는다

독립 DOCX에서 사용자A/B/C, 검증팀, 담당을 입력했다. 구조 미리보기는 카드
3개를 표시했다. 생성 결과는 A4 210.01×297.00mm와 25.4mm 여백, 1쪽,
표 0개, 이름과 소속의 6개 일반 문단이었다. evidence의 badge-generated-state,
badge-generated-structure 및 14-badge-generated-paragraphs.png로 확인 가능하다.

meetingTemplate는 heading/paragraph 쌍을 만든다. 카드 물리 크기·배치·용지
격자·재단/접힘선 계약은 없다. 현재 카드 미리보기의 '실제 크기·쪽 나눔은
생성 문서 확인' 안내는 제한을 정직하게 말하지만, 사용자가 선택한 업무인
'명찰 만들기'를 실제로 끝낼 수 있도록 해주지는 않는다.

개선:
- 현재 기능을 '명찰 내용 초안'이라고 표시하거나 실제 인쇄 템플릿을 제공한다.
- 인쇄 템플릿은 폭/높이 mm, 용지, 한 쪽 개수, 여백, 잘림/줄바꿈 기준을 가진다.
- 사람 이름이 길거나 소속이 두 줄일 때 크기 축소/줄바꿈을 미리 확인하게 한다.
- 미리보기 카드의 CSS 크기와 문서의 실제 치수를 혼동하지 않게 한다.
- 에이전트 요청에도 physical size와 layout을 명시하고 생성된 산출물로 검증한다.

HWPX 명찰을 별도로 생성한 결과는 이번 증거에 없다. 공통 템플릿의 부족과
DOCX 실제 결과를 구분한다. 일반 문서에서 문단으로 표현하는 용도는 정상이다.

5. P2: 노트북에서는 대조 작업의 공간이 부족하다

실제 샌드박스의 1366×768 화면에서 HWPX를 문서와 함께 보기로 바꾸었다.
iframe은 약 1024.6×258.7 CSS px이고 도구 탭 아래 입력은 스크롤 영역 밖의
아래쪽에 있었다. 본문/도구/입력 영역에 스크롤이 각각 생긴다. 도구 확대는
입력을 크게 만들지만 본문을 가린다. DOCX 목록 재진입은 오른쪽 모달을 열어
배경의 작업·채팅을 가렸다. 이 배치에서는 선택 위치를 보며 결과를 삽입하거나
에이전트 답변과 문서를 대조하기 어렵다.

styles.css:327의 1100px container 조건은 도구를 세로로 놓고 최대 42%를
배정한다. 호스트의 전역 사이드바, 작업 목록, 파일 모달 및 SDK 내부 툴바의
높이가 함께 영향을 준다. 모든 책임을 SDK CSS나 전역 모달 하나로 돌리지 않는다.

개선:
- 문서 작업에 들어가면 부수 탐색을 접을 수 있는 명확한 '문서 작업 모드'를 둔다.
- 도구 높이/너비를 사용자가 조절하고 최근 크기를 기억한다.
- 구조 미리보기/결과 대조 작업은 충분한 화면을 쓰고 일반 서식 조절은 compact로 둔다.
- 도구 확대에서도 선택된 문장의 발췌, 표 좌표와 적용 범위를 고정 표시한다.
- 채팅의 변경 항목을 클릭하면 문서 위치로 이동하는 연결을 제공한다.
- 확대/복귀는 문서 스크롤·선택을 보존해야 한다. 이번 시험으로 모든 문서의
  스크롤 보존이나 가로 넘침이 검증됐다고 주장하지 않는다.

6. P3: 입력·결과·구조 미리보기의 중복과 가독성

마크다운 원본, 읽기 전용 평문 textarea, 구조 미리보기가 세 표현으로 놓인다.
표·명찰 생성에서는 대부분 원본과 구조를 비교하고 싶다. 평문 결과가 큰
공간을 먼저 차지하고 구조 미리보기가 아래로 밀리면 개선 기능을 놓칠 수 있다.
생성 작업에서는 구조 미리보기를 기본 결과로 하고 평문은 '텍스트 결과' 탭이나
복사 버튼 안으로 옮기는 것이 좋다. 단순 계산 도구에서는 평문 결과를 유지한다.

실제 textarea의 computed font-size는 12px이고 도움말 CSS는 11px이다.
입력에는 길이 1,000,000까지를 상시 강조하지만 일상 입력의 열 이름·예시·오류
위치보다 우선도가 높게 보인다. 한도와 다운로드는 접을 수 있는 입력 보관
상태 영역으로 묶고, 일상적인 작성/미리보기/반영 행동을 우선 배치한다.
임의 WCAG 수치를 주장하지 않는다. 대비와 키보드 전체 순서는 후속 측정 대상이다.

DOCX의 'nothing to undo', 'the selection is not inside a table', 머리말/꼬리말
영문 지침이 그대로 노출된다. disabled 이유는 한글로 통일하고 '표 안의 셀을
선택하면 사용할 수 있습니다'처럼 다음 행동을 알려주는 편이 좋다.

7. P3: 도구 탐색과 산출물의 이름

20개 자동화 기능이 하나의 select에 있다. 사용 목적이 다른 금액·날짜 계산,
마크다운 보고서, 명찰, 추첨 등을 같은 깊이에 보여주면 처음 사용자에게
기능의 구분과 입력 형식이 잘 드러나지 않는다.

계산/표 정리/문서 작성/행사 자료/그림 등 목적별 묶음, 검색, 최근 사용,
입력 예시와 첫 결과를 제공한다. '보고서 작성 프롬프트'가 LLM을 실제 실행해
보고서를 만들어주는 기능인지, 요청 문장을 만드는 도구인지도 분명히 구분한다.
현재 core는 프롬프트 문자열 생성이다. 이를 실제 agent completion으로 세지 않는다.

실제 파일 목록에는 보고서-무작위8자리 파일들이 있다. 고유 이름은 충돌 방지에
도움이 되지만 생성 전 제목 기반 이름/저장 경로를 확인하는 UI가 필요하다.
목록에는 문서 제목과 형식, 생성 시각을 보여줘 여러 결과를 구분하게 한다.
서버 revision과 digest는 진단 정보이며 사용자에게 주 식별자가 될 필요는 없다.

8. 에이전트와 함께 쓰는 화면의 최소 설계

문서 헤더: 현재 파일과 저장 버전, 사람 편집/에이전트 편집/전환 중 상태.
에이전트 작업: 요청→수정 대상→제안/적용→저장 확정→결과 확인의 상태.
변경 표시: 어떤 문장/표가 어떻게 달라졌는지, 적용 범위와 취소/복구 방법.
오류 표시: 수정 실패와 저장 실패와 파일 목록 동기화 지연과 로컬 입력 보관
실패를 다른 단계로 설명한다. '다시 시도'는 실패한 단계만 재실행해야 한다.
완료 표시: '본문 변경됨'을 '서버 저장 완료'와 같은 문구로 보여주지 않는다.

기존 읽기 전용/lease 보호를 제거할 필요는 없다. 사람이 편집 중인 상태에서
에이전트가 임의 현재 선택을 덮어쓰는 동작을 막고, 누가 제어 중인지 보여줘야 한다.

9. 이번 리뷰의 검증 한계

사용자 업무 파일과 채팅에 새 내용을 쓰지 않았다. 실제 화면 탐색/원본 복구
관찰과 독립 엔진의 자체 문서 편집을 구분했다. 실제 서버 저장·새 파일 생성의
최종 검증 기록은 개발 세션에 있으나 이번에 같은 작업을 반복하지 않았다.
한컴/Word/프린터의 실제 인쇄 호환성을 검증하지 않았다. 카드 CSS 미리보기를
동일한 native 페이지 렌더링이라고 표현하지 않는다.

이번 실행은 SDK 단위 283개와 타입 검사, Chrome의 위 수동 재현이다.
개발 세션의 프론트 610개/Chrome·Edge 556개 결과는 이번 숫자와 별개다.
제품 소스는 수정하지 않았다. 임시 호스트와 증거는 .build에 보관한다.
