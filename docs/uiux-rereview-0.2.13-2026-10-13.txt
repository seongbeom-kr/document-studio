1. 사용자 경험에 대한 판정

0.2.12의 검색과 접힌 결과 영역 문제는 해결됐다. 원본과 구조 미리보기를
좌우로 비교할 수 있어 자동화 결과를 이해하고 적용하기가 쉬워졌다.
이번에 직접 관찰한 기본 흐름에서 새 P1/P2 문제는 발견하지 못했다.

다만 이 결과를 문서 업무 전체의 완성도 판정으로 확대하면 안 된다.
이번에는 실제 샌드박스의 도구 UI와 독립 호스트의 생성 결과를 검사했다.
실제 에이전트가 변경 제안, 적용, 서버 저장, 재열기까지 완료하는 사용자
경험은 아직 확인되지 않았다. 그 흐름이 현재 제품의 가장 큰 다음 과제다.

2. 실제 샌드박스에서 확인한 수정

대상은 기존 자체 검증 문서 '보고서-1eae3e27.hwpx'였다.
화면 크기는 1920×945 CSS px, 문서 배율은 100%였다.

검색: '내용 초안'을 입력하면 회의명패와 명찰 두 항목이 검색됐다.
현재 금액 한글화 기능은 선택과 입력을 보존하기 위해 계속 표시됐고,
검색 결과 개수에는 포함되지 않았다. '검색 결과 2개. 현재 선택과 입력을
유지합니다.' 안내로 현재 항목이 남는 이유를 이해할 수 있었다.

검색 결과 없음: 자체 검증용 무결과 검색어를 입력했을 때 결과 없음과
선택/입력 유지 안내가 표시됐다. 기존 금액 입력 12340은 사라지지 않았다.
검색이 기능을 강제로 전환하지 않아 작성 중인 입력을 보존하는 동작이다.

Markdown 구조 미리보기: 이 문서의 기본 27자 입력을 사용했다.
원본 입력과 구조 미리보기가 좌우로 표시됐다. 평문 결과 details는 두 열
grid 밖에 있고 접힌 상태 높이가 29px이었다. 이전 재현에서 차지했던
큰 빈 결과 열이 사라져 사용자에게 보이는 공간 낭비가 줄었다.

DOM 측정: 원본 x=1107, y=570.98, 폭=381.5, 높이=283.5px.
미리보기 x=1500.5, y=545.98, 폭=381.5, 높이=132.09px.
접힌 평문 결과 x=1107, y=862.48, 폭=775, 높이=29px.
측정 근거는 live-layout.json, 화면 근거는 01-live-improved-preview.png다.

3. 독립 실제 엔진 호스트에서 확인한 사용성

금액 한글화: 12340의 미리보기 결과는
'금12,340원(금일만이천삼백사십원)'이었다. 결과 필드는 readonly=false였고,
'검증용 결과'로 직접 바꾼 값도 표시됐다. 계산 결과를 그대로 쓰거나
문서 맥락에 맞게 다듬는 선택이 유지됐다.

차트: 기본 세 항목으로 미리보기 img 한 개가 표시됐다.
그림 삽입과 평문 삽입 버튼은 활성 상태였다. 차트의 실제 문서 삽입 및
내보낸 파일의 그림 품질까지 이번에 새로 검사한 것은 아니다.

구조 생성: 자체 Markdown의 2×2 표로 새 HWPX를 만들고 공개 inspect로
셀 4개, 행/열/병합 범위, 텍스트를 확인했다. 이는 독립 호스트의 생성
검증이며 실제 샌드박스 서버에 새 파일을 추가한 검증과는 구분한다.

4. 남은 P3: 차트에서 지원하지 않는 다음 행동을 안내한다

위치: packages/react/src/report-automation.tsx:786, 919.
재현: 새 문서 생성 callback이 연결된 독립 HWPX 호스트에서 차트를 선택하고
미리보기를 만든다. '구조를 유지해 새 문서 만들기'는 비활성 상태다.
그런데 공통 도움말에는 새 문서는 원본 입력으로 만든다는 설명과
'선택 위치에 넣거나 새 문서로 만드세요'라는 다음 행동이 표시된다.

영향: 결과를 만든 사용자가 비활성 버튼을 오류나 연결 문제로 오해할 수
있다. 삽입 가능한 결과 형식과 지원되는 작업이 안내에서 일치하지 않는다.
차트 자체는 graphic 결과를 만들고 DocumentTemplate는 만들지 않으므로
현재 새 문서 버튼의 비활성 처리는 지원 범위와 맞는다.

권장: 기능별 다음 행동을 표시한다. 차트에는 '현재 문서에 그림으로
삽입할 수 있습니다'처럼 실제 가능한 작업을 안내한다. 새 문서 생성이
불가능한 이유를 보여주거나 해당 기능에서 불필요한 버튼을 숨긴다.
완료 기준: 사용자가 도움말에서 안내받은 작업을 실제 활성 버튼으로
수행할 수 있다. 이 문제는 이번 버전의 새 회귀로 판정하지 않는다.

5. 사람이 쓰기 좋게 만드는 다음 작업 순서

첫째, 에이전트 변경의 대상과 완료 상태를 연결해야 한다.
사용자는 어느 문서의 어느 문단/표를 바꾸는지, 적용 전후 무엇이 다른지,
저장이 언제 확정됐는지를 한 흐름으로 이해할 수 있어야 한다.
채팅 변경 항목을 누르면 해당 문서 위치를 보여주고 저장 완료 시 파일
이름과 버전을 표시하는 방식이 유용하다. 이는 후속 설계 권고이며
현재 화면에서 새로운 결함으로 입증한 항목은 아니다.

둘째, 채팅·문서·도구의 전환 비용을 줄여야 한다.
문서 작업에 집중하는 모드, 도구를 접고 다시 펼쳐도 입력과 대상 선택을
잃지 않는 상태, 좁은 화면에서 문서와 변경 설명을 쉽게 전환하는 흐름이
필요하다. 이번 실제 화면 검사는 1920×945였으므로 좁은 화면의 완성도를
새로 인증하지 않는다. 이전 개발 세션의 반응형 테스트와 구분한다.

셋째, 인쇄 업무는 내용 초안과 완성 산출물의 경계를 유지해야 한다.
명찰/회의명패를 실제 출력 기능으로 확장할 때는 mm 치수, 용지, 한 쪽
개수, 격자, 재단선, 접힘선이 문서 계약에 포함돼야 한다. 이름 목록
생성과 실제 인쇄 배치의 성공은 별도 기준으로 검사해야 한다.

6. 검사 범위와 종료 상태

실제 샌드박스에서는 기존 자체 검증 문서의 검색/도구/미리보기를 조작했다.
문서 bytes, 채팅, 서버 파일은 변경하지 않았다. 종료 시 검색어를 비우고
금액 한글화 선택과 도구 닫기 상태로 복귀했다. 도구의 세션별 입력/선택
보관소에는 검증 중 선택한 기본 상태가 남을 수 있다.

독립 호스트는 실제 DOCX/RHWP 엔진과 공개 API를 사용했으며 저장은 메모리였다.
검증 탭과 임시 서버는 종료했다. 제품 소스를 수정하지 않았다.
물리 IME, 전체 접근성 준수, 실제 프린터, 모바일 전체 사용성을 검증하지 않았다.
