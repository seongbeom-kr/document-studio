판정

문서 편집 도구로서 이전보다 정돈됐다. 호스트 색상과 버튼, 한국어 도구명,
현재 선택에 따른 표 도구 안내, 수치 표시, 같은 편집 세션 안의 자동화 입력 보존이 좋아졌다.
예전의 불필요한 디자인 요소보다 현재는 '작업을 끝낼 수 있는가'와
'다음 행동을 사용자가 이해할 수 있는가'가 더 큰 문제다.

현재 상태를 '사람이 안심하고 쓰기 좋은 완성형 편집기'로 평가하지 않는다.
새 문서 생성이 실제 서버에서 막히고, 결과를 고치면 생성 버튼이 설명 없이 꺼지며,
편집기를 닫으면 자동화 입력은 저장된 문서와 별개로 사라진다.
이 문제들은 색상이나 여백을 다시 꾸미는 것으로 해결되지 않는다.

평가 방식

코드 적대적 리뷰와 이 UI UX 리뷰를 1:1 비중으로 구성했다.
발견 건수를 인위적으로 맞추기보다, 코드의 계약 안전성과 사용자의 작업 완료를 각각 평가했다.
이 문서는 버튼 존재 여부보다 입력 → 검토 → 적용/저장 → 재열기 → 실패 복구를 기준으로 삼았다.
UX 결함, 명시된 제한, 추가 개선 제안을 구분한다. 저장 문서 손상으로 과장하지 않는다.

구조 있는 template와 사람이 고친 평문 결과를 구분하는 구현 의도는 타당하다.
그 구분을 화면에서 설명하지 않아 사용자가 이해할 수 없는 것이 문제다.
오래된 template를 조용히 생성하는 방식으로 고치는 것도 적절하지 않다.

3. P2 자동화 입력은 편집 종료 시 사라지지만 문서 저장과의 차이가 충분히 드러나지 않는다

재현

HWPX 자동화 입력에 '# SDK HWPX 검증 20261008'과 검증 문장을 작성했다.
미리보기와 새 문서 생성 시도까지 진행한 뒤, 기존 문서는 정상 저장하고 편집을 종료했다.
같은 HWPX를 다시 편집으로 열고 마크다운 보고서를 선택했다.
입력은 '# 업무 보고서\n\n오늘의 업무 내용을 입력하세요.' 기본 예제로 돌아왔다.

영향

명단, 보고서 원고, 표 데이터를 길게 붙여 넣은 사용자는 입력을 다시 마련해야 한다.
'작업 공간에 저장'이 성공해도 자동화 폼의 원본 데이터까지 보관되는 것은 아니다.
특히 현재 생성 오류는 '편집을 닫고 다시 시도'하라고 안내한다.
그 안내대로 닫으면 실제 생성에 필요한 폼 입력이 사라져 복구 흐름도 나쁘다.

정확한 분류

도움말에는 '현재 편집 세션에서 기능별로 유지됩니다'라고 명시돼 있다.
따라서 영구 보존을 약속한 SDK 계약 위반으로 분류하지 않는다.
그러나 '편집 세션'이라는 말만으로 일반 사용자가 닫기 이후의 소실과
문서 저장의 범위를 이해하기는 어렵다. 실제 작업에 영향을 주는 UX 제한이다.
저장된 DOCX/HWPX 본문이 삭제되는 문제와도 구분한다.

또는 소유자/작업/문서/기능별 로컬 초안을 보관하고 재열기에서 복구하도록 한다.
문서 저장 성공 메시지와 자동화 입력의 보관 상태를 분리해 표시한다.
서버로 입력을 자동 전송하는 새로운 동작 없이도 로컬 초안으로 개선할 수 있다.

- 사용자/작업을 바꿨을 때 다른 사람 또는 다른 문서의 초안이 섞이지 않는다.

4. P2 탭 역할을 선언했지만 키보드 탭 동작과 패널 연결이 빠져 있다

직접 관찰

'표' 탭에 포커스를 놓고 ArrowRight를 눌렀다.
포커스와 선택이 계속 표에 남아 다음 '그림' 탭으로 이동하지 않았다.
8개 탭 모두 tabindex 지정이 없으므로 일반 버튼처럼 각각 Tab 순서에 들어간다.
각 tab의 aria-controls가 없고 대응 콘텐츠에는 연결된 tabpanel 역할이 없다.

키보드 사용자는 매번 여러 탭 버튼을 지나야 입력 필드에 도착한다.
스크린 리더에는 탭이라고 전달하면서 익숙한 탭 키보드 모델과 패널 관계는 제공하지 않는다.
마우스로 탭을 클릭하면 기능을 쓸 수 있지만 키보드 중심 문서 편집에서는 반복 비용이 크다.

코드

권장 개선

선택한 탭 하나만 Tab 진입점으로 두고, 방향키로 논리적 이전/다음 탭으로 이동한다.

tabpanel의 id와 aria-labelledby/aria-controls를 연결한다.

참조
W3C WAI ARIA Authoring Practices의 Tabs Pattern:
https://www.w3.org/WAI/ARIA/apg/patterns/tabs/
이 패턴과 관찰한 동작을 대조한 결과이며, 전체 WCAG 적합성 인증이나
스크린 리더 제품별 수용 시험을 수행했다는 뜻은 아니다.

완료 기준
- Tab은 선택 탭에서 패널 입력으로 이동한다.
- 방향키는 다른 탭으로 포커스를 이동한다.
- 스크린 리더가 선택 탭과 해당 패널의 관계를 읽을 수 있다.
- Shift+Tab, Escape, native 편집 영역 복귀가 자연스럽다.

6. 새 문서 생성 오류의 사용자 복구 흐름

기술적 P1의 사용자 경험은 다음과 같다.
- 현재 화면은 편집권을 확보했다고 표시한다.
- 같은 화면에서 새 문서를 만들면 다른 화면의 편집을 닫으라는 오류가 난다.
- 호스트와 SDK가 같은 오류를 각각 alert로 표시해 경고가 중복된다.
- 사용자는 어떤 화면을 닫아야 하는지 알 수 없다.
- 닫고 다시 열면 자동화 입력도 사라질 수 있다.

서버 계약을 고치는 것이 먼저다. 문구만 바꿔 실패를 정상 상태처럼 포장하면 안 된다.
그 다음 오류 표시의 소유자를 한 곳으로 정하고 원인·현재 보존 상태·재시도 행동을 함께 보여 준다.
예: 생성 실패 시 기존 문서는 보존됐는지, 생성 파일이 이미 저장됐는지,
다시 누르면 새로 업로드하는지 기존 산출물을 여는지 구분해야 한다.

7. 추가 제품 개선 제안

문서 템플릿의 결과 검토
현재 결과는 텍스트/탭 구분 형태다. 명단·명찰·조직도처럼 배치가 중요한 산출물은
평문 결과만으로 줄바꿈, 글자 크기, 쪽 넘김을 평가하기 어렵다.
우선 명단은 실제 표 미리보기, 명찰/명패는 카드 배치 미리보기를 제공하는 것이 좋다.
모든 기능에 큰 그래픽을 추가하기보다 산출물의 구조를 판단할 수 있는 최소 미리보기를 우선한다.

파일명과 위치
현재 생성 코드는 원문서의 폴더와 제목 기반 이름에 임의 접미사를 붙인다.
충돌 방지는 필요하지만 사용자는 저장될 이름과 위치를 결정하거나 확인할 수 있어야 한다.
실제 생성이 막혀 있으므로 생성 결과의 파일명 사용성은 코드 기반 제안이며,
이번에 실제 새 파일을 만들어 파일명 선택까지 수용 검증한 결과는 아니다.

주 행동의 구분
계산형 기능은 '계산 결과 삽입', 문서형 기능은 '새 문서 저장', 그림형 기능은
'그림 삽입'을 중심으로 보여 주면 기능마다 무엇을 얻는지 이해하기 쉽다.
20개 기능을 하나의 드롭다운에서 계속 탐색하는 방식은 가능하지만, 문서 작성/표 정리/계산처럼
작업 목적에 맞는 찾기 수단과 최근 사용 기능이 있으면 반복 업무에 도움이 된다.

SDK standalone 종료
닫기 확인창은 계속 편집/초안 다운로드/변경 버리고 닫기만 제공한다.
저장 후 닫기가 있으면 사용자가 확인창에서 돌아가 저장하고 다시 닫는 단계를 줄일 수 있다.
현재 샌드박스 호스트에는 저장 후 닫기가 있으므로 호스트의 미구현 문제로 분류하지 않는다.

8. 좋아진 부분과 유지할 설계

- 실제 호스트 색상과 기존 버튼 계층을 사용해 SDK의 별도 제품처럼 보이는 느낌이 줄었다.
- 문서 제목/저장 버튼이 중복되지 않는 embedded 구성이 맞다.
- 표 밖에서는 선택 안내를 먼저 보여 주고, 셀 선택 후 크기와 도구가 갱신된다.
- 수치는 읽기 쉬운 소수 자리로 표시하며 변경하지 않은 원래 정밀도를 보존한다.
- 명시적인 미리보기는 문서를 바로 바꾸지 않아 안전하게 결과를 살펴볼 수 있다.
- 같은 편집 세션에서 자동화 기능을 바꾸거나 도구를 다시 열어도 입력은 남는다.
- 이미지의 비율/본문 폭 안내와 인라인 배치 설명이 이전보다 명확하다.
- 지원하지 않는 Word 강조색을 공통 UI가 무조건 받지 않도록 제한한다.

9. 평가 한계 및 환경 관찰

브라우저는 기존 인증이 있는 Chrome을 사용했다.
노트북 크기는 viewport override로 검증했고 종료 전에 원래 크기로 되돌렸다.
실제 터치 기기, 스크린 리더, 물리 Windows 한글 IME 조합 시험은 수행하지 않았다.
한글 문장을 치환하고 저장/재열기하는 경로를 검증했으며 이를 물리 IME 검증으로 표현하지 않는다.

앱 콘솔에는 공통 runtime-layout active 조회 시간 초과와 기본 레이아웃 fallback 로그가 있었다.
이 UX 평가는 실제 표시된 화면을 기준으로 한다. 선택된 공통 레이아웃의 정상 수신 여부는
플랫폼 공통 영역의 별도 점검 사항이며 SDK 기능 결함으로 합산하지 않았다.

스크린샷에 작업 화면의 배경 대화가 함께 보일 수 있지만 대화 내용은 평가 대상이 아니다.
수정한 시험 대상은 이전 리뷰에서 만든 SDK-live-review-20261005.docx/.hwpx 두 파일이다.
생성에 쓴 인명과 문구는 이번 검증용 합성 데이터다.

우선순위

먼저 새 문서 생성이 실제로 끝나도록 한다.
동시에 결과 수정과 자동화 초안 보관의 상태를 사용자가 이해할 수 있게 한다.
그 다음 키보드 탭 모델과 좁은 화면 작업 공간을 개선한다.
색상/아이콘을 다시 바꾸는 작업보다 이 순서가 실제 업무 시간을 줄이는 데 더 효과적이다.
