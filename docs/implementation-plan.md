# 독립 오픈소스 문서 편집기 구현 계획

이 문서는 0.1.0 최초 계획입니다. 이후 0.2.0의 상세 계획·완료 범위는 [실사용 확장 계획](practical-editor-plan.md)과 [지원표](feature-support.md)에 반영했습니다.

별도 저장소에서 HWPX·DOCX 편집기와 공통 React UI를 개발하고, `automation-platform`이 배포된 패키지를 사용하도록 합니다. 첫 공개 버전은 HWPX·DOCX의 열기·편집·원본 형식 내보내기와 통일된 화면을 목표로 합니다. HWP·PPTX·XLSX는 같은 확장 구조에 단계적으로 추가합니다.

주 산출물은 기존 앱에 넣는 네 개의 SDK 패키지입니다. 기본 서식 명령, 저장·충돌·초안 복구와 에이전트 bridge를 구현했고 검증용 playground와 소비 예제를 제공합니다. 배포용 패키지와 소비 예제로 검증하며, 실제 실행 결과와 미검증 범위는 [검증 기록](validation.md)에 기록합니다. GitHub·npm 공개와 기존 운영 앱 교체는 후속 작업입니다. 선택 근거와 출처는 [오픈소스 조사](open-source-research.md)에 있습니다. 프로젝트명 `document-studio`와 패키지 이름은 가칭입니다.

## 제품과 배포 형태

라이브러리를 제품으로 배포하고, 예제는 소비·회귀 검증에 사용합니다.

| 형태       | 용도                         | 첫 버전의 역할                           |
| ---------- | ---------------------------- | ---------------------------------------- |
| Playground | SDK 개발·회귀 검증           | 테스트 문서 입력과 미저장·복구 흐름 검증 |
| React SDK  | 다른 React·Next.js 앱에 삽입 | 편집기·엔진 어댑터·저장 연결 API 제공    |
| 소비 예제  | 설치와 연동을 재현           | Vite 및 Next.js에서 배포 패키지 사용     |

Node는 개발·빌드·패키지 배포 도구로 사용합니다. 기본 편집에 서버를 필수로 두지 않습니다. 로그인, 저장소, 협업 서버, Office 변환 서비스는 소비 앱 또는 선택적 확장에 둡니다. 샌드박스에 연동할 때는 기존 인증·BFF·파일 저장 계약을 사용합니다.

자체 코드 라이선스는 Apache-2.0입니다. 기본 직접 엔진은 RHWP MIT, EigenPal core/React Apache-2.0이며, 상용 DOCX Pro·editor-api는 의존성에 넣지 않았습니다. 엔진 및 번들 자산의 LICENSE·NOTICE는 실제 고정 버전 기준으로 보관합니다. RHWP upstream 예제 문서·사진·서비스 워커와 별도 폰트 디렉터리는 런타임 패키지에서 제외합니다.

## 화면과 데이터의 경계

```text
automation-platform 또는 다른 소비 앱 (예제로 검증)
              │
              ▼
공통 React 편집 화면
파일 메뉴 · 툴바 · 문서 영역 · 상태 · 설정 · 대화상자
              │
              ▼
명령 · 선택 상태 · 기능 지원 · 내보내기 계약
       ┌──────┴──────┐
       ▼             ▼
RHWP 어댑터       DOCX 어댑터
HWPX 원본 모델    DOCX 원본 모델
       │             │
       └──────┬──────┘
              ▼
내보낸 bytes와 해당 편집 revision
              │
              ▼
호스트 저장 연결 또는 다운로드
```

각 엔진은 원본 형식의 모델과 직렬화를 담당합니다. 공통 JSON·HTML 문서 모델로 HWPX와 DOCX 전체를 변환하지 않습니다. 페이지 구조·표·필드·미지원 XML과 자산의 보존을 위해 원본 엔진을 유지합니다.

공통화하는 것은 UI 디자인, 열기·저장 흐름, 기본 명령 이름, 선택 상태, 기능 지원 정보, 오류·초안 상태입니다. HWPX와 DOCX의 의미가 다른 속성은 어댑터가 명시적으로 처리하고, 형식별 고급 기능은 별도 명령으로 확장합니다.

## 저장소와 기술 구성

```text
document-studio/
  apps/
    playground/             비공개 개발·회귀 검증 예제
  packages/
    core/                   형식, 명령, 상태, 저장 연결 계약
    react/                  공통 UI와 React 편집기
    engine-rhwp/            RHWP 초기화, bridge, 자산 연결
    engine-docx/            DOCX React/core 연결
  examples/
    nextjs/                 플랫폼과 같은 환경의 소비 예제
  fixtures/                 공개 가능한 자체 제작 문서
  docs/                     기능표, 설치, 확장, 호환성, 고지
```

후속으로 `engine-pptx`와 `engine-xlsx`를 추가합니다. 첫 단계부터 모든 형식의 패키지를 만들 필요는 없습니다.

개발 환경은 기존 플랫폼과 맞춰 Node 24·Yarn 4 workspaces·TypeScript strict를 제안합니다. 개발용 playground은 React 19·Vite로 시작하고, Next.js는 소비 예제에서 검증합니다. 재사용 SDK가 Next의 router·서버 기능에 의존하지 않도록 합니다. React는 peer dependency로 두어 소비 앱의 React 복사본과 충돌하지 않게 합니다.

UI는 React와 범위를 지정한 CSS로 구현했습니다. 배포 패키지가 CSS와 CSS 변수를 제공하며 소비 앱에 Tailwind·shadcn 설정을 요구하지 않습니다. 루트 아래에 스타일을 범위 지정하고 전역 reset을 넣지 않습니다. 색상·간격·한국어 메시지는 공통 UI에서 관리하고, 자체 대화상자는 키보드 포커스 제한·복원과 Escape 취소를 처리합니다.

RHWP Studio는 별도 정적 자산입니다. SDK·Studio·WASM의 고정 버전과 빌드 커밋을 함께 기록하고, 자산 경로를 소비 앱이 전달하도록 합니다. 패키지 설치 뒤 자동으로 외부 데모에 접속하는 동작을 기본값으로 두지 않습니다.

## 공통 명령과 상태 계약

첫 지원 명령은 전체 선택, undo·redo, 굵게·기울임·밑줄, 글꼴·크기, 문단 정렬·행간과 확대입니다. 글자색, 표 삽입·병합·분할, 페이지 이동과 고급 문단 속성은 후속 범위입니다. 기존 표·그림 등의 보존 검증과 새 객체 삽입 기능을 구분합니다.

| 계약          | 포함할 정보                                                  | 이유                                    |
| ------------- | ------------------------------------------------------------ | --------------------------------------- |
| 문서 입력     | id, 파일명, 형식, bytes, 외부 version                        | 파일 열기와 원본 버전을 분리해 추적     |
| 편집 snapshot | 로딩, 로컬 revision, 선택, 서식, 페이지, undo 가능 여부      | 공통 툴바와 상태 표시                   |
| 명령 상태     | 지원 여부, 현재 실행 가능 여부, active 또는 mixed, 제한 사유 | 선택 영역의 상태와 엔진 한계 표시       |
| 실행 결과     | 적용 여부, 새 revision, 실패 사유                            | 거절된 명령을 성공처럼 표시하지 않음    |
| 내보내기 결과 | bytes, 정확히 내보낸 revision, 형식, 경고                    | 저장 중 추가 편집과 저장 완료를 구분    |
| 저장 결과     | 저장된 외부 version 또는 conflict                            | 플랫폼의 서버 버전과 편집 revision 구분 |

서식 명령은 문자열과 임의 파라미터를 무제한으로 받지 않고 TypeScript discriminated union으로 정의합니다. 공통 글자 크기 단위는 pt로 정하고 원본 단위 변환은 형식 어댑터에 한정합니다. 호스트 API의 DTO 필드는 변환 없이 해당 API 계약을 그대로 사용합니다.

React 화면 연결과 순수 계약을 분리합니다. DOCX 어댑터는 `DocxEditor.Root` 아래에서 공개 hooks를 연결하고, RHWP 어댑터는 고정 iframe 안의 명령 bridge를 연결합니다. 자체 툴바 버튼이 선택 영역을 잃지 않게 하고, IME 입력 중 명령 실행·내보내기·문서 전환을 조정합니다.

다음 사용 형태는 제안 API이며 현재 구현된 API가 아닙니다.

```tsx
<DocumentEditor
  document={{ id, fileName, format, bytes, version }}
  engines={[
    rhwpEngine({ studioUrl: "/editor-assets/rhwp/index.html" }),
    docxEngine(),
  ]}
  storage={storage}
  onDirtyChange={handleDirtyChange}
/>
```

`storage`를 생략하면 내보내기·다운로드를 제공합니다. 파일 목록은 호스트가 소유하며, 편집 SDK는 특정 플랫폼의 목록 API나 세션 구조를 요구하지 않습니다. 원본 bytes 객체가 렌더마다 새로 생긴다는 이유로 편집기를 재마운트하지 않도록 문서 id·version과 교체 동작을 명시합니다.

## 첫 화면의 범위

공통 화면은 문서 제목·저장 상태·서식 툴바·문서 영역·상태 표시줄로 구성합니다. 개발용 playground에는 파일 입력과 빠른 서식을 추가했습니다. 첫 UI 언어는 한국어이며 영어 locale과 형식별 고급 메뉴는 후속 확장입니다.

RHWP는 기본 메뉴·툴바·상태표시줄을 숨기고 명령 bridge를 사용합니다. DOCX는 공식 composition API로 기본 chrome을 대체합니다. iframe 내부 DOM을 직접 찾아 버튼을 누르거나, 라이브러리 CSS를 광범위하게 덮어쓰는 방식에 제품 동작을 의존시키지 않습니다.

기본 UI가 숨겨져도 엔진의 내부 서식 대화상자가 나오는 명령은 있을 수 있습니다. 첫 릴리스에는 공통 입력 UI에서 파라미터를 전달할 수 있는 기능을 우선 제공합니다. 나머지는 공통 대화상자 연결을 구현한 뒤 추가하고, 필요 시 소규모 upstream 확장으로 해결합니다.

## 단계별 구현과 완료 기준

| 단계                   | 주요 작업                                                                       | 다음 단계로 넘어가는 기준                                                               |
| ---------------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 0 엔진 검증            | 배포 패키지 고정, 자체 호스팅 RHWP, UI 없는 두 편집기, 대표 명령·상태·저장 검증 | 동일한 React 버튼으로 두 형식의 편집·undo·저장·재열기 성공. 부족한 API와 수정 범위 기록 |
| 1 기반 구성            | workspaces, core 계약, 공통 UI, 데모, Next 소비 예제, 스타일·locale 연결        | 외부 앱에서 설치 가능하고 플랫폼 전용 import 없음. 두 편집기 상태를 같은 UI에서 표시    |
| 2 HWPX와 DOCX 편집     | 어댑터 명령 매핑, 선택·서식 구독, 파일 열기·다운로드, 지원 기능표               | 공개 fixture corpus에서 편집 후 원본 형식으로 재열림. 실패·미지원 상태가 드러남         |
| 3 저장과 복구          | 저장 연결, IndexedDB 초안, 저장 실패·충돌·새로고침·파일 전환 처리               | 저장 실패 시 초안 유지, 충돌 시 원본 덮어쓰기 방지, 복구 선택 가능                      |
| 4 패키지와 플랫폼 연동 | pack 산출물로 Next 예제 검증, 샌드박스 호스트 wrapper 연결                      | 실제 패키지로 기존 인증·lease·complete-edit·파일 갱신 흐름 유지                         |
| 5 첫 공개 릴리스       | README, 라이선스·NOTICE, 기능표, 기여 문서, 공개 fixture, 버전 정책             | 설치부터 개발용 playground 실행·플랫폼 삽입까지 재현 가능한 v0.1 배포 산출물 준비       |

0단계 결과가 전체 구현 범위와 공수를 결정합니다. 이 단계의 대상은 다음과 같습니다.

1. npm tarball의 실제 export와 동일 커밋의 Studio·WASM 연결을 확인합니다. `main` 문서의 기능과 설치 패키지의 기능이 같다고 가정하지 않습니다.
2. RHWP에서 글자 선택 후 외부 굵게·글꼴·정렬 명령을 실행하고, 선택 서식 조회·혼합 상태·undo·한글 IME를 확인합니다. `commands.context()`로 부족한 정보를 확인하고 작은 bridge 확장 후보를 기록합니다.
3. 일반 키보드 입력·붙여넣기·서식 변경·undo가 RHWP 변경 상태에 반영되는지 확인합니다. agent 전용 `onDocumentChanged`를 일반 편집 이벤트 대신 쓰지 않습니다. API가 부족하면 bounded 상태 조회 또는 일반 변경 이벤트 추가를 평가합니다.
4. DOCX의 무료 core/React API로 같은 동작을 구현합니다. Pro·editor-api 없이 가능한 범위를 확인합니다.
5. 각 형식에서 한글 문단·표·그림·페이지가 있는 자체 샘플을 수정하고 저장·재열기합니다. 파일 구조와 표시 결과를 각각 기록합니다.
6. 두 편집기를 한 화면에 동시에 두고 명령·단축키·스타일이 다른 인스턴스에 전달되지 않는지 확인합니다.

첫 검증이 부족하면 결과에 따라 확장점을 보완하거나 해당 기능을 첫 버전의 지원 목록에서 뺍니다. 파서와 조판 엔진 전체를 새로 만들겠다는 약속으로 넘어가지 않습니다.

## 저장 상태와 초안 처리

저장 흐름은 `편집 중 → 내보내기 snapshot 생성 → 호스트 저장 → 해당 snapshot 저장 완료 표시`입니다. 내보내기 동안 편집을 잠시 멈추거나 엔진이 보장하는 일관된 snapshot을 사용합니다. 저장 요청 뒤 새 편집이 생겼다면 완료 응답이 와도 현재 문서는 미저장 상태로 남아야 합니다.

외부 `version`은 저장소가 관리하는 토큰이고 로컬 `revision`은 편집기가 관리하는 값입니다. 저장 연결은 `expectedVersion`을 전달하고 저장된 새 버전을 반환합니다. `409` 같은 충돌은 명시적 conflict로 연결합니다. 최신 파일 보기·내 초안 다운로드·명시적 재열기 선택을 제공하고 조용히 덮어쓰지 않습니다.

초안은 IndexedDB에 저장하되 호스트·사용자·문서별 namespace와 원본 version을 함께 기록합니다. 복구 데이터가 현재 원본과 다르면 충돌 상태로 표시합니다. 저장소 사용 불가·용량 초과·내보내기 실패를 알리고, 주기적 저장 전에 갑자기 종료된 편집까지 복구할 수 있다고 안내하지 않습니다.

원본 교체, 실패 후 재시도, 저장 완료 후 목록 갱신 실패는 서로 다른 상태입니다. 특히 저장 성공 후 목록 조회만 실패한 경우 저장 실패로 오인해 다시 업로드하지 않도록 분리합니다.

## automation-platform 연동 계획

독립 패키지는 `@packages/ui`, `config-client`, `session`, `service-client`, `workAgentApi`를 import하지 않습니다. 플랫폼의 인증 정보·세션 id·서버 주소는 공개 SDK의 기본 설정에 포함하지 않습니다.

샌드박스 쪽에 작은 호스트 wrapper를 둡니다. wrapper가 BFF로 bytes를 읽고, 편집 session·lease·digest를 확보한 뒤 SDK에 파일을 제공합니다. 저장 연결은 현재 업로드와 `complete-edit` 경로를 사용하고, 서버가 성공한 뒤 파일 목록·미리보기를 갱신합니다. 기존 충돌·실패·초안 조건을 유지합니다.

운영 앱 연동은 소비 프로젝트에서 호스트 wrapper를 연결하고 실제 저장 경로를 검증하는 별도 단계입니다. 현재 제공한 예제와 단위 테스트는 호출 계약을 확인한 범위이며 운영 앱의 인증·네트워크·동기화 검증을 대신하지 않습니다.

개발 중에는 로컬 package pack 산출물로 연동합니다. 릴리스 이후에는 정확한 버전을 고정하고 엔진도 함께 고정합니다. 저장소의 소스 경로나 실행 중인 데모 URL에 장기적으로 의존하지 않습니다. Next.js client boundary, 동적 로딩, basePath, 자산 경로와 CSP 요구를 소비 예제로 검증합니다.

## 공개 저장소와 유지보수

공개 산출물은 엔진 연결 코드·공통 UI·데모·소비 예제·기능표·고지·합성 fixture입니다. 기본 설치가 상용 모듈을 요구하지 않게 하고, 선택적 플러그인은 별도 문서와 의존성으로 분리합니다.

엔진 결함은 최소 재현 파일과 regression 조건으로 관리합니다. 가능한 수정은 upstream에 제안하고, 임시 패치는 원인·적용 버전·제거 조건을 기록합니다. 특히 기존 PPTX 테마 폰트 패치와 XLSX 줄바꿈 대응은 새로운 upstream 버전에서 문제가 해결됐는지 확인한 뒤 변경합니다.

GitHub 저장소 공개와 npm publish는 후속 릴리스 작업입니다. 현재 로컬 독립 프로젝트와 tarball을 준비했으며 외부 계정에 저장소를 만들거나 공개 배포하지 않았습니다. 실제 공개 대상과 패키지 이름을 정한 뒤 준비된 산출물로 릴리스를 진행할 수 있습니다.

## 후속 형식 확장

| 순서      | 형식 | 후보와 선행 조건                                                           | 첫 확장 범위                                                       |
| --------- | ---- | -------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| v0.2 후보 | HWP  | RHWP. OLE/binary 원본 저장과 독립 재열기 검증                              | HWP 원본 편집·저장. 페이지 수 확인만으로 전체 보존을 판정하지 않음 |
| v0.3 후보 | PPTX | pptx-viewer/core. 기존 패치 회귀, 테마·마스터·도형 보존, 공통 UI 제어 검증 | 기존 슬라이드 텍스트·기본 객체 편집부터 시작                       |
| v0.4 후보 | XLSX | office-kit 파일 처리 + FortuneSheet 또는 Univer OSS 화면을 비교            | 값·서식·시트·기본 수식. 계산·표시·파일 보존 지원을 분리            |

PPTX는 headless core가 있다고 해서 캔버스 선택·도형 편집·리본 UI까지 바로 공통화되는 것은 아닙니다. 후속 단계에서 공개 UI 확장 API를 확인하고 필요한 화면 연결을 설계합니다.

XLSX에서 Univer를 선택하면 무료 파일 처리 계층과 Univer 모델의 매핑을 직접 구현하고, 미지원 원본 구조를 보존해야 합니다. FortuneSheet를 선택해도 공식 import/export 플러그인의 보존 수준을 검증해야 합니다. 기존 AG Grid 방식은 제한된 셀 편집 대안으로 남기며, 실시간 수식 계산·차트 편집을 구현했다고 간주하지 않습니다.

서버 협업, AI 수정 제안, 변경 추적·댓글 작성, PDF 내용 편집은 첫 릴리스 뒤 별도의 기능·엔진·라이선스 범위를 정해 추가합니다. 이 확장 때문에 기본 HWPX·DOCX 사용에 서버나 유료 패키지가 필수가 되지 않도록 분리합니다.

## 첫 구현 결과와 다음 작업

통일된 서식·행간·저장 화면, 형식별 어댑터, 합성 검증 문서, 에이전트 API와 소비 예제를 구현했습니다. `examples/sandbox-agent/storage.ts`에는 기존 업로드 함수의 계약을 유지하는 호스트 연결과 단위 테스트를 제공합니다. 운영 앱의 실제 네트워크·lease 갱신·BFF 환경을 검증한 결과는 아닙니다.

다음 제품 확장은 범정부 오피스의 반복 서식 자동화 방향을 참고한 문단 앞뒤 간격·들여쓰기·번호 목록·표 서식과 에이전트의 문서 위치 지정입니다. 형식 확장은 위의 HWP → PPTX → XLSX 순서로 진행합니다. 각 추가 기능은 명령 지원 정보, 실제 저장 결과와 회귀 문서를 함께 갱신합니다.
