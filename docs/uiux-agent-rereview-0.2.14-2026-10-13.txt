1. 결론

0.2.13에서 남긴 차트의 다음 행동 안내 P3는 해결을 확인했다.
차트와 조직도 그림은 그림 삽입을 안내하고 새 문서 생성 버튼을 표시하지 않는다.
계산 결과는 편집 가능한 텍스트 삽입을 안내한다. 문서 템플릿은 호스트의
생성 지원 상태에 맞춰 생성 안내와 버튼 상태를 바꾼다.

이번 코드·실제 화면·독립 엔진 검사에서 새 P1/P2 결함은 발견하지 못했다.
두 형식의 정상 수정, 오래된 선택 거절, 저장 digest, 차트 실제 삽입,
생성 지원 전환 후 2×2 표 생성도 확인했다.

남은 P3 사용성 문제는 실제 1366×900 화면의 기본 도구 높이다.
도구 전체 높이 195.5px 중 본문은 42px여서 자동화 폼이 거의 가려진다.
'도구 크게 보기'를 누르면 본문 448.5px로 작업할 수 있으므로 기능 차단은
아니다. 처음부터 입력·결과·다음 행동을 이해하기 쉬운 기본 배치가 필요하다.

최종 목적에 대한 큰 미완료 항목은 실제 General→열린 SDK 도구 연결이다.
SDK 자체의 동작과 에이전트 업무 완료는 별도 기준이다. 실제 LLM 호출,
서버 저장, 재열기로 결과를 확정하는 시험은 아직 수행하지 못했다.

2. 이전 P3 해결 근거

실제 샌드박스에서 기존 자체 파일 sdk-live-B.hwpx를 열었다.
DOM의 data-document-studio-version은 0.2.14였다.
차트 미리보기 그림은 1개, 새 문서 생성 버튼은 0개였다.
도움말은 현재 문서에 그림으로 삽입할 수 있고 텍스트도 별도 삽입할 수
있다고 안내했다. 지원하지 않는 새 문서 생성을 다음 행동으로 제안하지 않았다.

독립 DOCX/HWPX 호스트에서도 조직도 그림·차트의 생성 버튼 0개를 확인했다.
호스트 생성 지원을 꺼도 그림 삽입은 가능했다. DOCX 계산 결과를 직접
수정할 수 있었고 생성 버튼은 없었다.
Markdown은 생성 지원을 끄면 버튼이 비활성이고 지원하지 않는 이유가
표시됐다. 지원을 켜면 입력을 유지한 채 버튼이 활성화됐다.

3. 이번 직접 실행 검증

- SDK 단위 테스트 287/287, yarn typecheck 통과.
- 소비 프론트 네 SDK 패키지는 모두 0.2.14다.
- 설치된 dist 95개 전체의 SHA-256이 SDK 빌드와 일치한다.
- 소스/extension manifest 49개는 검사 시작·종료 해시가 같았다.
- DOCX/HWPX: 첫 문단 요청 고정 후 두 번째 문단으로 이동하면 선택 충돌로 거절.
- DOCX/HWPX: 정상 요청은 첫 문장만 [[AGENT-INSERT]]로 바꾸고 두 번째 문장 보존.
- DOCX/HWPX: commit digest와 메모리 storage에 제출한 bytes의 SHA-256 일치,
  commit 이후 dirty=false.
- DOCX/HWPX: 차트 그림을 실제 삽입하고 내보낸 XML에서 그림 객체 1개 확인.
- DOCX/HWPX: 호스트 생성 지원 꺼짐→켜짐 후 실제 새 문서 생성,
  inspect에서 2행×2열·셀 4개와 텍스트 확인.

개발 세션의 프론트 610개·관련 Chrome/Edge 48개·외부 소비 앱 4개는
별도 결과다. 이번에 직접 재실행한 숫자에 합산하지 않는다.
전체 브라우저 회귀가 이번 수정에서 새로 전부 통과한 것으로 표시하지 않는다.

4. P3: 노트북 폭의 기본 도구 본문이 너무 낮다

재현: 실제 샌드박스의 sdk-live-B.hwpx 편집기, 1366×900 CSS px,
도구 영역 크기 34, 업무 자동화 탭, 확장하지 않은 상태.
도구 전체 높이 195.5px, 헤더 높이 51px, 본문 높이 42px였다.
목표 안내·크기 조절·탭이 공간을 사용하고 자동화 폼은 작은 스크롤 영역에 남는다.
그 상태에서 기능 선택이나 원본 입력을 바로 발견하기 어렵다.

관련 위치: packages/react/src/styles.css:360–362.
1100px 이하 편집기 container에서 도구를 세로 배치하고 높이를 비율로 정한다.
default 34%와 고정 안내/탭 영역의 조합이 이번 실제 화면의 낮은 본문 높이를 만든다.
기본값은 packages/react/src/editing-tools.tsx:67–70에서 확인할 수 있다.

권장: 비율 외에 폼 본문의 최소 가용 높이를 확보하거나, 낮은 높이에서
업무 자동화 탭을 열면 확장 모드로 시작한다. 반복 안내/크기 조절은 접을
수 있게 하되 적용 대상과 주요 행동은 계속 보이게 한다.
완료 기준: 같은 화면과 기본 설정에서 기능 선택, 원본 입력, 미리보기 행동을
사용자가 좁은 내부 영역을 먼저 스크롤하지 않고 발견할 수 있다.

완화 수단: '도구 크게 보기' 후 전체 575px, 본문 448.5px였다.
기능 사용은 가능하므로 P1/P2가 아닌 낮은 우선순위의 사용성 문제다.
이번 안내 수정의 새 회귀로 판정하지 않고 기존 기본 배치의 남은 문제로 분류한다.

5. 실제 에이전트 연결에서 확인해야 하는 계약

HWPX 차트 삽입 직후 즉시 export 기반 검사를 요청했을 때
'문서를 내보내는 동안 revision이 변경됐습니다. 다시 내보내 주세요.'가 반환됐다.
비동기 삽입 완료 후 재검사는 그림 1개를 확인했고 저장도 성공했다.
SDK가 불일치한 revision의 문서를 성공으로 반환하지 않은 보호 동작이다.

실제 도구 transport는 execute 완료, 변경 revision 확정, commit, inspect,
서버 재열기를 순서대로 연결해야 한다. 선택 충돌이면 대상을 다시 확인하고,
revision 충돌이면 안정된 버전으로 재조회해야 한다. 명령을 무조건 반복해
중복 삽입하지 않도록 오류별 다음 행동을 정해야 한다.

소비 프론트의 production TS/TSX에서 createAgentBridge/expectedSelectionKey
등록을 확인하지 못했다. General Python에서도 SDK 관련 등록을 확인하지 못했다.
프론트에는 DocumentEditor와 storage 연결이 존재한다. 에이전트 도구 연결의
완료와 구분한다. 기존 파일 에이전트의 다른 기능을 부정하는 판단은 아니다.

6. 다음 우선순위

1) 실제 General 도구 호출과 서버 재열기까지 완료하는 작은 문서 업무 시험.
2) 기본 도구 본문의 가용 높이 개선 및 채팅 변경 항목과 문서 위치 연결.
3) 명찰/회의명패의 실제 인쇄 배치: mm 치수·용지·배치·재단/접힘선 계약.

7. 범위와 종료 상태

실제 샌드박스에서는 기존 자체 검증 파일의 UI를 확인했다. 문서 bytes,
채팅, 서버 파일을 변경하거나 새 파일을 업로드하지 않았다.
Markdown 원본 92자를 유지했고 파일의 표시 해시와 revision 7도 유지됐다.
종료 시 편집을 끝내고 파일 목록으로 복귀했으며 viewport override를 해제했다.
독립 호스트의 수정·삽입·생성·저장은 자체 합성 문서와 메모리 저장소에서 수행했다.
독립 검증 탭과 임시 서버를 종료했다. 제품 소스·커밋·푸시·배포는 변경하지 않았다.

이번 실제 화면의 반응형 검사는 1366×900이다. 480px·모바일 전체,
전체 접근성 준수, 물리 IME, Word/한컴/프린터, 운영 장애는 미검증이다.
이전 중첩 표/검색 수정은 변경 없는 코드와 0.2.13 직접 재현 결과를 참고했다.
이번에 그 모든 재현을 다시 실행한 것으로 표시하지 않는다.
