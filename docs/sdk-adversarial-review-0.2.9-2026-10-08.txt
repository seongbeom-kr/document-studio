판정

0.2.9의 공통 쓰기 가드, 새 문서 생성 순서, 자동화 초안 저장을 검토했다.

새로 확인한 결함은 P2 1건이다.
자동화 입력은 1,000,001자를 저장 성공으로 처리하지만, 같은 자료를 다시 불러올 때
자체 검증에서 거절한다. 저장과 읽기의 값 계약이 일치하지 않는다.

1. P2 저장 성공으로 표시한 자동화 초안이 다음 열기에서 손상 자료로 거절됨

재현

실제 AutomationSession 클래스와 AutomationDraftStore 계약을 사용하는 경계 시험을 작성했다.
store 구현은 structuredClone으로 값을 보관하는 Map 대역이다.

1) session.start()로 정상 시작한다.
2) 마크다운 보고서 입력에 ASCII 1,000,001자를 넣는다.
3) flush()를 호출한다.
4) store.put이 한 번 호출되고 session 상태가 ready=true, pending=false, error=''가 된다.
5) 세션을 종료하고 같은 store/key로 새 AutomationSession을 만든다.
6) 새 start()가 '자동화 초안 값이 올바르지 않습니다.'로 실패한다.

대조 시험
같은 경로에서 1,000,000자는 저장·재열기 모두 성공했다.
따라서 무작위 저장소 고장이나 코드 로딩 실패와 구분되는 정확한 크기 경계다.
신규 시험 2개 중 대조 1개 통과, 계약 검증 1개 실패.

상황으로 한정되지 않는다.

사용자 영향

큰 원고나 표 데이터를 붙여 넣으면 현재 세션에서는 보관 완료로 보일 수 있지만,
다음 열기에 해당 초안의 복구가 막힌다.
읽기 검증은 drafts 전체를 검사하므로 한 기능의 긴 입력이 같은 기록에 있는 다른 기능의
정상 입력 복구까지 막을 수 있다.
자료를 자동 삭제하는 것은 아니며 원본 상태는 저장소에 남는다.
그러나 일반 UI에서 복구되지 않는 문제이며, 이를 영구 데이터 삭제라고 표현하지 않는다.

SDK의 save/flushDraft는 automationSession.flush를 기다린다.
복구 오류가 나면 기본 문서 저장/전환도 이 의존성 때문에 실패할 수 있어,
단순한 글자 수 안내 문제보다 영향이 넓다.
이 추가 영향은 코드 경로 확인이며 대용량 실제 서버 문서 저장을 재현한 결과는 아니다.

검증 한계

1,000,001자 경계의 직접 재현은 store 대역을 사용한 클래스 시험이다.
Chrome IndexedDB에 대용량 기록을 넣는 시험이나 실제 서버 업로드 시험은 수행하지 않았다.
실제 IndexedDB는 일반 크기의 입력을 보관·닫기·재열기하는 경로를 별도로 검증했다.
이 결함은 storage가 성공한 값이 스스로의 reader에서 거절된다는 계약 불일치에 관한 것이다.

수정 방향

- 읽기와 쓰기에 같은 AutomationDraftState 검증기를 적용한다.
- 저장할 수 없는 입력이면 저장 완료로 표시하거나 기존 정상 초안을 덮어쓰지 않는다.
- 입력 한도와 현재 길이를 화면에 알려 주고, 초과 입력을 조용히 잘라내지 않는다.
- 현재 입력을 수정하거나 내려받을 수 있도록 유지한다.
- 손상 기록을 버리는 경로만 제공하기보다 원본 자료의 안전한 다운로드/개별 복구를 검토한다.

완료 기준

1,000,000자와 1,000,001자 각각에 대해 writer/reader 계약이 일치해야 한다.
초과 값을 거절하는 정책이라면 쓰기 전에 명시적으로 거절하고 이전 정상 초안은 보존한다.
허용하는 정책이라면 다음 열기에서 같은 값이 복구되어야 한다.
둘 이상의 기능을 보관한 기록에서 한 입력의 오류가 정상 자료의 복구 경로를 없애지 않아야 한다.

4. 새 저장 기능과 전환 코드에서 확인한 방어

- 자동화 입력 저장소는 opt-in이고 문서 bytes와 분리돼 있다.
- 샌드박스는 owner/workspace/document 범위를 키에 연결한다.
- 입력 보관은 직렬화된 write 체인과 revision으로 관리하고 실패 시 pending을 유지한다.
- 초기 읽기 실패/손상 자료는 자동 덮어쓰기하지 않는다.
- 이전 비동기 작업의 실패도 저장 대기에서 놓치지 않도록 선행 Promise를 고정한다.
- 새 문서 업로드 완료 응답 유실과 실제 파일 저장/후속 열기를 구분하는 재시도 상태가 남아 있다.

가용성 설계 검토 사항
문서 저장과 자동화 입력 저장이 한 Promise의 성공 조건으로 묶여 있다.
입력 유실 방지는 필요하지만 선택 기능의 저장소 장애가 일반 문서 저장에도 영향을 준다.
문서 저장 완료와 자동화 입력 보관 실패를 분리해 전달하면서, 입력이 남은 상태의 전환은
보호하는 API/호스트 계약을 검토할 가치가 있다. 이 정책 자체를 별도의 새 결함으로 집계하지 않았다.
