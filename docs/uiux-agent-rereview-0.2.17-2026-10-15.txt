1. 결론

이전 P2인 'HWPX 초기 iframe load의 무제한 대기'는 이번에 확인한 경로에서
해결됐다. 기본 제한 시간으로 실패 상태에 진입하고 iframe을 제거하며, 공개
에이전트 API와 화면의 재시도 모두 복구에 성공했다. 이 P2는 종료 판정한다.

실제 sdk-live-B.hwpx는 첫 연결에서 다시 시간 초과가 났다. 그러나 이번에는
준비 실패 안내와 다시 시도 버튼이 나왔고, 다시 시도한 뒤 정상적으로 열려
기존 92자 자동화 원본과 표 미리보기를 사용할 수 있었다. 첫 연결이 지연되는
근본 원인까지 해결됐다는 뜻은 아니다. 정확한 원인은 여전히 미확정이다.

UI/UX의 이전 입력 가림도 재현되지 않았다. 반면 실제 에이전트 시험은 실패했다.
별도 검증 작업에서 SDK 편집·저장을 요청했고, 편집권 반환→요청 접수까지는
진행됐지만 이후 오류로 일시정지했다. SDK getState→select→execute→commit의
실제 호출 기록과 서버 편집 성공을 얻지 못했다. '에이전트가 이 SDK를 실제로
잘 쓴다'는 최종 목표는 아직 미완료다.

신규 UI/UX 지적은 P3 한 건이다. 도구 결과가 표시되지 않는 실패에도 '도구 결과를
확인'하라는 안내만 나와 사용자가 원인과 다음 행동을 알기 어렵다. 이번 SDK
변경에서 새 P0/P1/P2 코드 결함은 확인하지 못했다. 통합 미완료와 회귀를 구분한다.

2. HWPX 수정 검토와 직접 재현

엔진 전체 초기화 기본 30초 제한, AbortController를 통한 취소, failed/loading/
ready 상태, 재시도 API가 추가됐다. load뿐 아니라 handshake/ready/chrome 설정/
loadFile/확장 준비/첫 상태 확인을 제한한다. 초기 검증 worker의 제한은 별도다.
의존성 @rhwp/editor 0.8.6은 빌드 시 고정 SHA를 확인해 취소 가능한 코드로
번들한다. SDK 배포본에 패치가 포함되며 소비자가 node_modules를 수정하지 않는다.

독립 호스트는 소스 alias 대신 네 패키지의 빌드 dist를 사용했다. 정상 provenance를
유지하고 iframe HTML 응답만 보류했다. 브라우저 시계 가속 없이 실제 시간을
진행시켰다. 새 문서 요청 후 약 31.8초에 이미 failed인 것을 관찰했고, 41.5초에
저장한 스냅샷에도 같은 상태와 iframe 0개가 남아 있었다. 정확한 타이머 발화
시각을 측정했다는 의미는 아니다.

공개 getState의 오류는 engine-initialization-timeout, retryable=true였다.
실패 후 flushDraft는 내보내기 없이 종료 준비를 완료했다. 지연을 해제하고
agent.retryInitialization을 실행하자 즉시 loading/connecting과 새 sessionId가
반환 상태에 반영됐고, 이후 ready가 됐다. 이전 실패 세션으로 다시 재시도하면
'대상 편집 세션이 변경됐습니다'로 거절됐다.

실제 사이트에서도 첫 실패 때 iframe이 제거되고 준비 실패 footer가 표시됐다.
사용자가 누르는 '편집기 다시 시도'로 정상 복구했다. 실패 원인을 파일 손상이나
사용자 네트워크 문제로 단정하지 않는 안내 방향도 적절하다.

5. SDK 자체의 정상·적대적 경로

공개 createAgentBridge를 호출하는 검증 UI로 다음을 직접 확인했다.
- 두 형식: 원본 입력/미리보기/키보드 보정/크기 변경 후 선택·세션·revision·dirty·zoom 보존.
- HWPX: 선택을 다른 문장으로 옮기면 이전 토큰의 명령 거절.
- 두 형식: 고정한 guard의 insertText가 첫 문장만 교체하고 두 번째 문장은 유지.
- 두 형식: commit digest와 실제 메모리 저장 bytes의 SHA-256 일치, dirty=false.
- HWPX: 저장 실패를 표시하고 같은 요청을 재시도해 성공. 완료 요청 재호출은 추가 저장 없음.
- 두 형식: 저장 bytes로 새 documentId/key/session의 편집기를 열어 첫 문장 변경 보존.
  새 세션의 revision 0을 확인했다. 기존 편집 세션에서 재읽기만 한 결과와 구분했다.

이는 실제 엔진과 메모리 저장소를 사용한 SDK 시험이다. 실제 General LLM이나
서버 저장 성공으로 바꾸어 표현하지 않는다. SDK 상세 문서에 호출 조건을 남겼다.

7. 최종 제품 방향 대조 — 사용자의 추가 세션을 확인한 뒤 보완

참조한 Codex 세션: 01a13d13-cf4b-7d33-bc69-33c474a0aee9
현재 내용을 read_thread로 읽고 제품 소스와 대조했다. 목표는 특정 샌드박스의
부속 화면을 만드는 것이 아니라, 여러 프론트 앱에서 사람이 편집·편의기능을
쓰고 에이전트도 같은 기능을 안전하게 호출하는 문서 편집기 SDK다.

책임 경계는 해당 세션의 정리와 일치해야 한다.
- SDK: 문서 열기/상태/대상 지정/명령/편의기능/내보내기·저장 계약/복구.
- 소비 앱: 로그인·권한 판단/저장소/LLM·MCP transport/편집권 정책/앱 화면.
SDK에 LLM 서비스를 내장하는 것이 목표는 아니다. 이번 실제 에이전트 실패는
소비 앱 통합 검증이 통과하지 못했다는 뜻이며, SDK 자체의 신규 결함으로
분류하지 않았다. 반대로 SDK 단위·메모리 저장 통과만으로 최종 제품을 완성했다고
판정할 수도 없다. 최소 하나의 실제 소비 앱이 계약을 끝까지 증명해야 한다.

현재 상태를 다음처럼 구분한다.
A. 공통 기반: core는 React 의존 없이 문서/명령/서식·계산 함수를 제공한다.
B. 임베드: 공개 편집기와 엔진 View 계약은 React 19 중심이다. Vue/일반 JS가
   DOM 요소에 mount/destroy하는 범용 진입점은 현재 공개 export에서 확인되지 않았다.
C. UI 구성: appearance=embedded와 테마 연동은 있지만 DocumentEditorProps에
   toolbar/panel slot이나 교체 renderer 계약은 없고 기본 UI가 컴포넌트 안에 있다.
D. 편의기능: 계산·표·템플릿 함수는 core에 있으나 기능 선택→입력 해석→결과 생성
   조합은 report-automation.tsx의 generate/switch에 남는다. agent bridge는
   listAutomationForms로 계약 목록을 제공하지만 같은 업무 기능 전체를 공통 실행
   API로 호출하는 dispatcher는 현재 bridge에서 확인하지 못했다.
E. 에이전트: 조회/검색/선택/보호된 명령/commit/초기화 재시도의 기반은 있으며
   이번 독립 엔진 검증은 통과했다. 실제 호스트 연결과 업무 전체 완료는 미검증이다.

개발 순서는 세션의 제안에 대체로 동의하지만, 실제 에이전트 검증을 모든 구조
개편의 마지막에만 두는 것은 권하지 않는다. 먼저 최소한의 한 문장 수정→저장→
재열기 경로를 실제 호스트에서 증명하고 이 경로를 이후 단계마다 유지해야 한다.
계약 누락과 저장소/권한 문제를 초기에 발견하기 위한 기준이다.

권장 순서:
1) 공통 editor session/controller와 사람·에이전트의 명령/결과 계약을 정한다.
2) 기존 React 내부 구현을 재사용하는 DOM mount/update/destroy 진입점을 제공한다.
   React/Vue/일반 JS 호스트가 같은 반환 handle을 사용하게 한다.
3) 기본 UI를 바로 쓸 수 있게 유지하면서 toolbar/panel을 구성·교체할 수 있게 한다.
4) 편의기능의 입력 검증/결과 생성/대상 적용을 공통 작업 API로 올린다.
5) React와 Vue 등 두 소비 앱에서 사람→에이전트→저장·재열기를 실제 검증한다.
실제 호스트의 최소 에이전트 경로는 1단계부터 병행한다.

이는 현재 방향의 점검과 권고이며 이번 리뷰에서 범용 임베드나 LLM transport를
새로 구현한 것은 아니다. 현재 확인한 기준으로는 '기반이 마련된 React 중심 SDK,
범용 임베드·공통 편의작업 API·실제 소비 앱 에이전트 통합이 남음'이 정확한 상태다.
