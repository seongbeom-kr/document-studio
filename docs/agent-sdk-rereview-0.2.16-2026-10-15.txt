1. 결론

0.2.16의 제품 변경은 UI 배치에 한정된다. core, engine-docx/src,
engine-rhwp/src, agent-bridge.ts는 0.2.15와 같다. 그럼에도 '작동할 때의 SDK'
외에 '준비되지 않을 때의 SDK'를 검사한 결과 P2 한 건을 확인했다.
HWPX의 첫 iframe load가 오지 않으면 초기화가 끝나지도 실패하지도 않는다.

정상 경로의 대상 지정·삽입·메모리 commit은 두 실제 엔진에서 통과했다.
이 결과는 SDK 사용 가능성의 근거이며, 실제 LLM이 올바른 도구를 선택하고
서버에 반영하는 전체 업무 성공률의 근거는 아니다.

2. P2 — 엔진 초기화 전체를 제한하고 실패 상태를 전달해야 한다

SDK 위치: packages/engine-rhwp/src/index.tsx:379-382
현재 await createStudio(container, options)를 감싸는 전체 deadline/취소가 없다.
반환된 created가 있어야 editor가 할당되고, 그 뒤 chrome 설정과 loadFile이 실행된다.

의존성 @rhwp/editor 0.8.6, node_modules/@rhwp/editor/index.js:69-72는
iframe.addEventListener('load', resolve, { once: true })만으로 기다린다.
이 대기에는 timeout/reject 분기가 없다. transport.connect 및 _waitReady는
그 뒤에 실행된다. 기존 handshake/request timeout이 없는 것으로 오해하면 안 된다.
문제는 그 timeout에 진입하기 전의 무제한 대기다.

SDK의 catch(717-721)는 reject가 발생해야만 onError를 호출한다.
cleanup(724-739)은 active를 내리고 message/pending/calls를 정리하지만,
아직 await가 반환하지 않아 editor가 없는 경우 editor.destroy도 실행되지 않는다.
초기화 취소를 추가할 때 반환 전 iframe과 리스너의 수명도 함께 다뤄야 한다.
이번에는 실제 메모리 누수의 크기를 측정한 것이 아니므로 누수량을 주장하지 않는다.

3. 정상 경로에서 직접 검증한 계약

자체 검증 호스트의 UI 버튼이 공개 createAgentBridge를 호출했다.
브라우저 evaluate로 SDK 내부 상태를 조작하지 않았다. 정상 엔진과 메모리
DocumentStorage를 사용했다. 서버 저장, 백엔드 mock으로 대체한 실제 서비스
성공 판정, General LLM 도구 호출은 수행하지 않았다.

두 형식 공통:
1) 첫 문장을 search/select하고 전체 요청 기준을 고정했다.
2) 업무 자동화의 입력/미리보기/키보드 보정/세 가지 CSS 크기를 거쳤다.
3) sessionId, revision, selectionKey, dirty=false, zoom=1이 유지됐다.
4) 고정된 documentId/expectedSessionId/expectedVersion/expectedRevision/
   expectedSelectionKey로 insertText를 호출했다.
5) 첫 문장만 [[AGENT-INSERT]]가 되고 두 번째 문장은 보존됐다.
6) commit 후 dirty=false이며 receipt.digest와 실제 저장 bytes의 SHA-256이 같았다.

DOCX: revision 0→1. HWPX: 0→2. 증가량을 한 번의 요청=1이라고 가정하지 않았다.
선택 전체 교체는 고정된 선택 범위에 insertText를 실행한 의도된 결과다.
현재 자동화 마크다운을 편집하는 동작이 문서 내용 revision을 올리지 않은 것도
예상한 계약이다. 이 두 편집 상태를 에이전트가 혼동하지 않도록 문서화해야 한다.

DOCX는 동일 operationId로 commit을 재호출했고 같은 version/digest가 반환됐다.
저장소 호출 누계는 2를 유지했다. 앞선 HWPX 1회+DOCX 1회인 공유 호스트 누계다.
HWPX의 commit 재시도와 실제 서버 idempotency는 이번에 별도 재실행하지 않았다.

4. 자동화 원본과 문서 변경의 경계

미리보기만 만든 동안 현재 문서의 dirty/revision은 유지됐다. 두 형식에서
선택 토큰도 보존돼 UI 조작 뒤 고정한 명령이 정확한 대상에 적용됐다.
이 경계는 에이전트가 작업을 수행할 때 중요하다. '결과 만들기'와 '현재 문서에
반영하기', '새 문서 만들기', '서버 저장하기'를 도구 계약에서 명확히 구별해야 한다.

이번에는 마크다운 구조 미리보기와 기존 문서의 guard 삽입/commit을 검사했다.
0.2.16 개발자 기록의 새 문서 생성·inspect 확장 테스트는 소스를 검토했으나
전체 Chrome/Edge 묶음을 직접 재실행한 것은 아니다. 이를 새 문서 서버 저장·
재열기까지 이번에 완료했다는 주장으로 바꾸지 않는다.

5. 에이전트가 실제로 이 SDK를 쓰는 목표까지의 거리

소비 프론트 DocumentStudioPanel은 DocumentEditor ref와 편집 잠금/handoff 확인,
저장 callback을 연결한다. 현재 제품 TS/TSX 검색에서는 createAgentBridge와
expectedSelectionKey 참조가 0이었다. 이것은 조사한 프론트의 연결 범위에 대한
증거다. 별도 서비스의 모든 문서 도구 구현이 없다는 증명은 아니다.

따라서 다음 실증이 아직 필요하다.
- 실제 General LLM이 열린 문서의 상태/기능을 읽는다.
- 검색/선택 후 session/revision/selection guard를 포함한 호출을 보낸다.
- 사용자가 대상을 옮기거나 파일을 바꾸면 stale 호출이 적용되지 않는다.
- 성공한 명령의 결과를 읽고 commit receipt를 실제 서버 저장 결과와 연결한다.
- 저장된 파일을 다시 열어 의도한 범위만 바뀌었는지 확인한다.
- 초기화 실패/응답 지연/저장 실패는 재시도 가능한 결과로 종료된다.

최소 DOCX/HWPX 각각 정상 경로 한 건과 선택 변경·연결 지연·저장 재시도 경로를
실제 도구 trace로 남기는 것이 다음 완료 기준으로 적절하다. LLM에게 내부 ID를
추측하게 하지 말고 도구 응답의 대상과 guard를 다음 호출에 전달하게 해야 한다.
