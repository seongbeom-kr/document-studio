1. 이번 사용성 판정

HWPX가 멈췄을 때 계속 기다리기만 하던 경험은 개선됐다. 실제 첫 연결이 다시
실패했지만 이번에는 이유를 단정하지 않는 시간 초과 안내와 다시 시도 버튼이
나왔다. 버튼을 누르자 실제 문서가 열렸고 자동화 원본과 표 결과도 유지됐다.
오류를 숨기는 대신 실패를 인식하고 회복할 길을 준 점은 적절하다.

다만 '첫 클릭에서 바로 열린다'는 안정성은 아직 보장하지 못했다. 이번에도
첫 연결 실패가 있었고 근본 원인은 미확정이다. 사용자가 다시 시도 버튼을
써야 했다는 사실과, 복구 기능이 정상이라는 사실을 함께 기록한다.

2. HWPX 초기화의 사용자 흐름

실제 sdk-live-B.hwpx를 기존 작업에서 열었다. 서버 preview/raw는 200이었으나
첫 native 연결은 시간 초과가 났다. SDK는 iframe을 제거하고 실패 안내를
표시했으며 프론트 footer도 '편집기 준비 실패'로 바뀌었다. 실패 상태에서
다운로드/저장 버튼은 비활성이라 준비되지 않은 문서를 저장했다고 오해하지 않는다.

'편집기 다시 시도' 뒤 도구들이 활성화되고 두 쪽 문서가 열렸다. 자동화에
기존 92자 원본이 남아 있었고 제목·문단·표·표 뒤 문단을 미리보기로 확인했다.
기존 내용 자체는 수정하지 않았다. 정상 복구 뒤 편집→미리보기로 돌아가는
흐름도 완료됐다. 이전 무한 대기에 대한 P2는 이 범위에서 종료한다.

독립 배포 dist 호스트에서도 기본 30초 설정으로 연결 응답을 보류했다.
시계 가속 없이 실패/재시도 안내와 iframe 제거를 확인했고, 네트워크 지연을
해제한 뒤 공개 API 재시도로 정상 편집이 가능했다. 자동 재시도를 무한 반복하는
동작은 없었다. 실제 첫 연결 지연의 원인과는 구분한 복구 검증이다.

3. 이전 입력 가림은 계속 해결 상태

독립 DOCX/HWPX, CSS 1366×768 / 호스트 1023×514:
업무 자동화 자동 확장, 결과 생성 후 입력 노출 약 140.3px, position=static.
입력 안쪽 +4/+40/+79px에 textarea가 적중했다. 원본 제목을 키보드로 수정하고
다시 미리보기를 생성해 결과 제목이 바뀌는 것까지 확인했다.

독립 DOCX/HWPX, CSS 480×900 / 호스트 456×700:
결과 후 약 177.4px가 노출됐고 같은 적중 검사가 통과했다. 검사한 도구 영역의
가로 넘침은 없었다. DOCX의 CSS 1366×900 / 호스트 1023×646은 약 270px였다.
HWPX의 보통 높이 조건을 이번에 별도로 측정했다고 주장하지 않는다.

실제 별도 검증 작업의 HWPX, CSS 1366×768 / 편집기 약 1024×537.3:
자동 확장 후 입력 약 172.6px, 적중 세 지점 모두 textarea, 가로 넘침 없음.
기본 27자 자동화 원본의 결과를 생성했다. 현재 문서 bytes는 바꾸지 않았다.
04-actual-hwpx-low-ui.jpg가 이 화면의 증거다.

4. P3 — 도구 결과가 없는 실패에서 '도구 결과 확인' 안내

실제 재현은 별도 검증 작업에서 SDK를 통한 한 문장 편집을 요청한 것이다.
'저장하고 요청 실행' 확인 후 읽기 전용 미리보기로 전환되고 요청이 접수됐다.
잠시 working으로 표시되다가 일시정지로 끝났으며, 도구 결과 카드나 원인별
안내 없이 아래 일반 오류 안내가 표시됐다. 이 실패의 내부 원인은 미확정이다.

관련 코드:
D:\dev\_worktrees\document-studio-0.2.11\apps\sandbox-agent\lib\work-agent\tool-presentation.ts:200-207
현재 일부 알려진 오류만 개별 안내로 바꾸고 나머지는 일괄적으로 도구 결과를
확인하라고 한다. 실제로 확인할 결과가 없는 경우 사용자는 다음 행동을 정하기
어렵다. 다시 요청하면 되는지, 연결을 설정해야 하는지, 문서를 다시 열어야
하는지 알 수 없고 관리자에게 전달할 실행 확인 번호도 화면에서 찾기 어렵다.

권고:
- 도구 호출 전/실행 중/저장 중 실패를 안전한 범주로 구분한다.
- 결과가 있을 때만 결과 확인으로 연결한다. 없으면 그 사실을 명시한다.
- 민감한 원본 예외 대신 지원용 실행 확인 번호와 기록 열기/복사 기능을 제공한다.
- 요청을 보존해 재시도할 수 있게 하되 이미 성공한 변경이 중복 실행되지 않게 한다.
- SDK 연결 미지원 상태라면 요청 실행 전에 가능한 작업과 제한을 알려 준다.
이번 변경에서 유입된 회귀로 특정한 것은 아니다. 현재 실패 경험에서 확인한 P3다.

5. 실제 에이전트 흐름의 기대와 화면 동작

사용자는 열린 문서의 선택 범위를 AI에게 넘긴다고 이해할 수 있다. 실제 화면은
편집 중인 문서를 종료하고 서버 에이전트에게 요청을 전달한다. 파일 기반 작업을
넘기는 흐름과 살아 있는 SDK 세션을 조작하는 흐름은 사용자 기대가 다르다.

현재의 저장·편집권 보호를 해제하라는 제안은 아니다. 에이전트가 받을 문서와
선택 대상, 저장 방식, 작업 중 사람이 편집 가능한 범위를 명시할 필요가 있다.
SDK 경로가 준비되지 않았다면 프롬프트에 SDK 함수명을 적는 것만으로 작동하지
않는다는 점도 제품에서 설명해야 한다. 이번 실제 요청은 성공하지 않았으므로
사용자가 완료된 문서를 얻는 경험까지는 미완료로 판정한다.

6. 후속 개선 제안

A. 기다리는 동안 현재 단계와 빠져나오는 행동을 함께 보여 준다.
loading 단계 구분은 추가됐지만 30초는 체감상 길다. 불확실한 진행률을 꾸미기보다
'편집기에 연결 중/문서를 여는 중'과 취소·파일 목록으로 돌아가기를 제공한다.
초기화 실패를 파일 손상으로 단정하지 않는 현재 문구는 유지하는 편이 좋다.

B. 낮은 창에서는 원본/결과 확대 전환을 제공한다.
가림은 해결됐지만 140px는 긴 문서 원본을 대조하기에는 짧다. 결과 확인과
원본 보정에 각각 공간을 몰아줄 수 있으면 좋다. 적용 영역을 다시 sticky로
만들어 입력 공간을 덮는 방식은 피해야 한다.

C. 원본 보관·문서 반영·서버 저장을 가까이에서 구분한다.
자동화 초안이 브라우저에 보관됐다는 상태와 현재 문서에 삽입됐다는 상태,
작업 공간 서버에 저장됐다는 상태를 사용자가 한눈에 이어 읽을 수 있게 한다.
내부 ID·토큰·해시는 일반 화면 대신 개발자 진단에 두는 편이 적절하다.

7. 검증 범위

Chrome 실제 샌드박스와 독립 dist 호스트에서 확인했다. 좁은 viewport는 모바일
입력 가림 검사이며 실제 휴대폰 키보드·터치 업무 전체 검증은 아니다. 전체
접근성·물리 IME·Word/한컴 왕복·인쇄 품질은 이번 결과로 보증하지 않는다.
기존 다섯 파일과 새 합성 두 파일의 원본 해시/리비전은 유지됐다.
